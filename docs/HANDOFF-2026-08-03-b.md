fission sites from an engine simulating millions.

## 7. WHAT TO WATCH OUT FOR (traps + hard-won insights — read every one)

### 7.1 The density-coupling insight (the single most important one)
`Σ ∝ ρ` (`number_density = frac·ρ/Mbar·N_A`, and `RefTransport` recomputes number
densities from `Material.density` at construction). So a *bigger* sphere at *fixed*
density reads as MORE reactive (less leakage) — **backwards** for disassembly, and
wrong for compression. For ANY moving geometry you MUST scale density with the
geometry (mass-conserving: `ρ/ρ₀ = (r₀/r)³`). **Use `ref_eigen_fn_masscons`, never
`ref_eigen_fn`, whenever the geometry moves.** `ref_eigen_fn` (fixed density) is only
for a static assembly. This was the crux of step 3 and it will bite step 5 (the full
device) too — there it needs *per-layer* density scaling (the current mass-cons
adapter is uniform, exact only for a bare core).

### 7.2 Unit consistency (the disassembly crux)
The disassembly is SI: `E_n` in Joules (`= F_n · e_f_joules`, `e_f_joules = C-040·C-917`),
core mass in kg, `R` in metres, `P` in Pa; geometry radii are cm; the radius scale
is dimensionless. The physical energy scale sets the disassembly *timescale/yield*.
The self-limiting-burst test uses a **test-scale `core_mass_kg` (0.05)** so it quenches
in seconds; the *physical* ~kg core gives the real (longer) timescale + yield. This
is a test-speed choice (like `batch=2000` vs `1e6`), not faking — the mechanism is real.

### 7.3 The shared working tree with the -e (visualizer) session
The parallel viz session has been developing in the SAME working tree (`C:\NUCLEAR`),
so its uncommitted `viz/` edits (and `.zcode/`) appear in your `git status`. **Rules:**
stage EXPLICIT paths (`git add <path> …`), NEVER `git add -A` from the repo root;
verify `git diff --cached --name-only` has no `viz/`/`zcode` before every commit;
`git checkout -b` at HEAD is safe (no working-tree change), but be aware branch
switches change the branch under -e too. A worktree **`C:/nuclear-viz`** (branch
`viz/gadgetlab`) has been created for -e; its `viz/` work migration is the owner's to
run when -e is idle. `C:/nukeviz` is the standalone GadgetLab *runtime* build (not a
git tree) — leave it.

### 7.4 The `fast4` discipline (never cross this line)
`fast4` = the cited 4-group cross-section dataset (~450 physical values, M1-T4a-2).
It is **owner-provided** and **MUST NOT be invented** — fabricated cross sections are
the single failure the entire provenance discipline exists to prevent (they'd make
the gates compare the code against numbers someone made up, invisible in review).
BLK-14 forbids an autonomous session seeking ICSBEP access. If you need cited Pu xs
and it isn't there, use synthetic-but-loadable xs (tagged SIM, like `RealSphere`) and

### 7.5 CI / git cadence
Space out pushes to `main` — three rapid pushes trigger a GitHub Actions concurrency
cancel-cascade (benign but confusing). Watch a push's CI to green before layering the
next task on it (the pattern this session used). **gcc (Linux CI) finds what MSVC
does not** (`-Wdangling-reference`, `-Wsign-compare`, unused-static) — expect it on new
modules; MSVC-clean is not CI-clean. `ctest --preset` writes `Testing/Temporary/` into
the repo root (gitignored). Use `git commit -F -` with a heredoc (backticks in `-m`
execute). Merge to `main` only green (`--no-ff` merge commit, message via a temp file —
`git merge -F <file>`; `-F -`/stdin does NOT work for `git merge`).

### 7.6 Protocol traps (from `docs/ONBOARDING.md §4` — the ones that recur)
Read the module spec (`04`/`05`), not just the data contract (`03`). A "within 1σ"
acceptance threshold is a coin flip (use 3σ + a mean-pull bias check). Never tune a

be anchored (`^<module>\.`). Constants from `data/constants.toml` / `ns::consts`, never
magic numbers; gate thresholds from `gates.toml`.
