### BLK-01 — Tier-1 compression formula is algebraically wrong; radius collapses to zero at t₀

**File/section:** `01-physics.md` §5 Tier-1 (mirrored in `05-module-transport.md` §4 Tier-1)

**What is wrong.** The formula is

```
r(t) = r_0 · (1 + (ρ/ρ₀)^{1/3} − 1)^{-1} · s(t)
```

`1 + x − 1 = x`, so the bracket is `(ρ/ρ₀)^{1/3}` and the expression reduces to `r_0·(ρ/ρ₀)^{-1/3}·s(t)`. For r₀ = 4.585 cm, ρ/ρ₀ = 2.2:

| s(t) | r(t) |
|---|---|
| 0.0 | **0.0000 cm** |
| 0.5 | 1.7627 cm |
| 1.0 | 3.5253 cm |

The endpoint is correct; the start is a point singularity. The smoothstep scales the whole radius instead of interpolating between initial and final radii.

**Why it matters.** Tier-1 drives **G1a and G1b** (`08-validation.md` §2 specifies both as Tier-1) and M2-T2/M2-T3. Implemented verbatim, every point on the M2-T3 `k(ρ/ρ₀)` curve is wrong — and M2-T2's DoD ("2× compression conserves mass per layer") **passes anyway**, because a uniform scale conserves mass at any s. The bug is invisible to its own test.

**Fix.** Replace the geometry line with

```
r(t) = r_0 · [ 1 + ( (ρ/ρ₀)^{-1/3} − 1 ) · s(t) ]     # s: 0→1 smoothstep over [t0, t0+t_c]
```

and strengthen M2-T2's DoD: *"unit test asserts r(t₀) = r₀ for every layer to 1e-12; r(t₀+t_c) = r₀·(ρ/ρ₀)^(−1/3); per-layer mass constant to 1e-12 at s ∈ {0, 0.25, 0.5, 0.75, 1}."* The mass check alone does not catch this class of error.

### BLK-02 — The normative main loop exits on its first iteration

**File/section:** `02-architecture.md` §3; interacts with `01-physics.md` §6

**What is wrong.** The loop is a do-while whose exit predicate is `until k < 0.998 (quench) or t ≥ t_max`. At t₀ the assembly is uncompressed and **k ≈ 0.89** — G1a's own band is [0.70, 0.95]. The predicate is true after the first generation; the burst terminates with F_cum ≈ 0.

Underneath sits a second defect: **t₀ is never defined**, and both readings break something.

- *t₀ = start of implosion* — the loop exits immediately, and 500 generations of `E3_step` would otherwise run through a subcritical phase.
- *t₀ = peak compression* — the loop survives, but the compression phase is never simulated, contradicting D6's staged clock, Tier-1's `s(t)` over `[t0, t0+t_c]`, Tier-2's converging phase, and `HydroModel::at_peak_compression()` (which exists to *drive* `t_fire`, implying the sim runs before peak compression).

**Why it matters.** This is the top-level control flow, marked "normative pseudocode". M3-T3's DoD ("canonical scenario end-to-end artifact bundle emitted") is satisfied by a bundle with zero yield, and the failure presents as a physics problem.

**Fix.** Add an explicit phase state and gate the quench test on it:

```
t = t0_implosion ; n = 0 ; supercritical_reached = false ; F_peak = 0
loop:
    if (n mod M == 0) or hydro_dirty:  k, Lambda = eigen(geometry); hydro_dirty = false
    if k >= 1.0: supercritical_reached = true
    N, F_gen, E_gen = E3_step(k, N, S_n, nu_bar, E_f)
    F_peak = max(F_peak, F_gen)
    ...
    n += 1 ; t += Lambda                       # BLK-04
until (supercritical_reached and F_gen < eps_quench * F_peak)   # BLK-03
   or t >= t_max
```

and define t₀ normatively in `03-data-contracts.md` §4: *"t = 0 is the instant the outermost HE surface is initiated; `initiator.t_fire_s` is measured relative to `HydroModel::at_peak_compression()`."*

### BLK-03 — Quenching at k < 0.998 discards roughly half the yield

**File/section:** `01-physics.md` §6 (E6, first bullet); `02-architecture.md` §3; `07-milestones.md` M3-T2/M3-T3; `08-validation.md` §2 G2

**What is wrong.** The spec terminates the burn when k crosses below 1 (hysteresis 0.998). In fast-burst kinetics, k = 1 is the moment of **peak power**, not the end of energy release.

The Fuchs–Nordheim model is exactly the physics E3a + E4 implement (exponential multiplication with feedback linear in deposited energy):

```
dN/dt = (α₀ − bE)·N ,  dE/dt = c·N   ⟹   N(E) = [α₀E − bE²/2]/c + N₀
```

`N` peaks at `E = α₀/b`, which is precisely where net reactivity — and therefore α and k − 1 — passes through zero; the burn ends at `E = 2α₀/b`. **Exactly half the total energy is released after k drops below 1.**

**Why it matters.** The project's headline number is low by ~2×. Worse, **G2 hides it rather than catching it**: an implementer whose yield lands near 10 kt will reach for the free knobs (`compression.ratio`, the XS set, `c_a`) until yield enters [15, 25] kt, producing a model that passes with two compensating errors — the circular-calibration failure R-2 warns about, arriving through a door R-2 does not watch.

**Fix.**

1. `01-physics.md` §6, first bullet →
   > The chain reaction **peaks** when k(t) crosses 1 and continues into a decaying phase. The burn terminates when the per-generation fission rate has decayed to a negligible fraction of its peak: `F_n < ε_quench · max_m F_m`, `ε_quench = 1e-4` (`constants.toml`, `SIM`), or when `t > t_max`. `quench_k` marks entry to the decay phase; it MUST NOT terminate integration. `tally.json` reports F_cum split pre-/post-peak (a healthy Tier-2 disassembly gives a post-peak fraction of order 0.3–0.5).
2. `03-data-contracts.md` §5: add `"yield_split": {"pre_peak_kt": …, "post_peak_kt": …}`.
3. `08-validation.md` §4 (non-gating): *"post-peak yield fraction reported; below 0.15 indicates premature termination."*

### BLK-04 — Generation time is a fixed constant; it must scale with density, and the eigen interface cannot return it

**File/section:** `01-physics.md` §1 (`g ≈ 10 ns`), §4 (`t += g`); `03-data-contracts.md` §4 (`kinetics.generation_time_s`); `05-module-transport.md` §2 (`EigenResult`)

**What is wrong.** `g` is a scenario scalar fixed for the whole run. The prompt generation time is `Λ = ℓ/k` with `ℓ ≈ 1/(v Σ_t)`, so `Λ ∝ 1/ρ`. The canonical scenario compresses by ρ/ρ₀ = 2.2, which **more than halves** Λ. Holding g = 10 ns underestimates α = (k−1)/Λ by ≈ 2× through the entire supercritical phase.

The error does not stay in the timebase: the hydro integrates on sim time while multiplication integrates per generation, so a 2× error in Λ gives the assembly ~2× the disassembly time per e-folding. The yield error is first-order and in the **same direction** as BLK-03.

Compounding it, `EigenResult` is `{k, sigma_pcm, k_history, H_history, source}` — **no field for Λ, ℓ, or α.** The interface cannot return the quantity. Meanwhile `10-ui.md` Panel 3 requires a "Rossi-α readout", and `01-physics.md` §1 defines α = (k−1)/g then never uses it in any equation.

**Why it matters.** M3-T1's DoD ("fixed k = 2, ν̄ = 2.9 ⇒ F_n matches closed form") passes with a wrong Λ, because Λ never appears in the per-generation recursion. The error stays invisible until G2, where knob-tuning absorbs it.

**Fix.**

1. `05-module-transport.md` §2:
   ```cpp
   struct EigenResult { double k, sigma_pcm;
                        double lambda_s;     // prompt generation time Λ = ℓ/k [s]
                        double lifetime_s;   // mean prompt lifetime ℓ         [s]
                        double alpha_per_s;  // (k−1)/Λ
                        std::vector<double> k_history, H_history;
                        FissionSource source; };
   ```
   plus: *"Λ is estimated from the active generations with a track-length time estimator: accumulate Σ(path length)/v per history from birth to progeny birth, divide by k."*
2. `01-physics.md` §4: replace `t += g` with `t += Λ(t)`, and add **E3b**: *"Λ is returned by every eigen refresh and held constant between refreshes. `kinetics.generation_time_s` is the initial value only, used before the first eigen call and for Tier-1 UI display; it MUST NOT be read afterwards."*
3. Rename the field `kinetics.generation_time_s` → `kinetics.generation_time_s_initial`.
4. M1-T3 DoD addition: *"Λ decreases monotonically with pit density at fixed geometry, and Λ(2ρ)/Λ(ρ) ∈ [0.4, 0.6]."*

### BLK-05 — E1c's fission-bank formula contradicts its own sampling scheme and contradicts `05-module-transport.md`

**File/section:** `01-physics.md` §2 (E1c) vs `05-module-transport.md` §1

**What is wrong.** Three statements are mutually incompatible:

| Location | Says |
|---|---|
| `01` §2 header | "Monte Carlo **with implicit capture (weight-based)**" |
| `01` §2 E1c | "reaction sampled from group XS shares … Fission: **kill incoming neutron**, bank `⌊w·ν̄·(Σ_f/Σ_t)·(1/k_gen) + ξ⌋`" |
| `05` §1 | "sample reaction ∝ σ shares; … fission → deposit **weight·ν̄·(1/k)** progeny" |

`w·ν̄·(Σ_f/Σ_t)/k` is the **implicit** (expected-value) contribution, valid only when applied at *every* collision without branching. `w·ν̄/k` is the **analog** contribution, valid only inside a branch already selected with probability Σ_f/Σ_t.

E1c does both — analog branch selection *and* the Σ_f/Σ_t factor. That double-counts the fission probability and yields **k low by a factor ≈ Σ_f/Σ_t ≈ 0.2–0.3** for a metal system. With analog absorption weights never fall, so `w_min = 1e-4` / `w_surv = 1e-2` are dead code and "implicit capture" in the header is false.

**Why it matters.** This is *the* estimator: k ≈ 0.25 instead of 1.0 on Godiva. It blocks M1-T2 and M1-T3, and the two files a session would open for the same task disagree — so the failure mode is silent divergence depending on which file was read.

**Fix.** Pick one scheme and state it in both files. Recommended (implicit capture — better variance, matches the header and the roulette parameters). `01-physics.md` §2, replace E1c:

> **E1c (collision, implicit capture):** sample the isotope ∝ n_i·σ_t,i. Bank `⌊ w·ν̄·(Σ_f/Σ_t)·(1/k_gen) + ξ ⌋` progeny (eigenvalue) or push the same count onto the stack (fixed source), then reduce weight for absorption: `w ← w·(Σ_s/Σ_t)`. The neutron is **not** killed at fission. Scatter isotropically-in-lab (MAJ-31) with group transfer per the transfer matrix. Apply Russian roulette when `w < w_min`. Analog absorption is NOT used; `sigma_a` never terminates a history directly.

`05-module-transport.md` §1 becomes a verbatim pointer to E1c. Add to M1-T2's DoD: *"unit test: for a homogeneous infinite medium the estimated k_inf equals ν̄·Σ_f/Σ_a analytically within 3σ."* That catches this class of error immediately; the specified leakage test does not.

### BLK-09 — `tools/gen_constants` cannot run against its own seed data; the appendix is not machine-readable

**File/section:** `appendix/constants.md` §1, §3; `03-data-contracts.md` §1; `04-module-core.md` §1; `07-milestones.md` M0-T3

   hi     = 2.5
   unit   = "ratio"
   status = "DECLASSIFIED"      # PUBLIC | DECLASSIFIED | RECONSTRUCTED | SIM | PENDING

### BLK-11 — The GPU design cannot be deterministic, but three normative requirements demand that it is

2. **Monotonicity.** "k monotone non-decreasing over ρ/ρ₀ ∈ [1.0, 2.0]" is asserted on an MC-sampled curve with σ ≈ 25 pcm per point. Strict monotonicity on noisy samples **fails at random**, at a rate rising with scan-point count. `08 §3`'s anti-seed-shopping rule then forbids re-running, so the project deadlocks on a statistical artifact.

**Why it matters.** G1b certifies the compression model before kinetics. As written it is simultaneously too tight (the 1.5 cliff), too loose (no upper bound), and randomly flaky.

**Fix.**

> **G1b** — canonical scenario, Tier-1, `compression.ratio` scanned over {1.0, 1.2, …, 2.0}. Pass iff **all**:
> 1. `M_pit/M_c(2ρ₀) ∈ [2.6, 4.4]` (public "3–4 critical masses", C-053, ±40 % reflecting that the source is prose);
> 2. `k(2.0) ∈ [1.35, 1.85]` — derived band, tagged `SIM` in `gates.toml`, derivation recorded;

### MAJ-17 — G0c's statistical criteria are flaky, partly impossible, and get stricter the more you test

**File/section:** `08-validation.md` §2 G0c; `05-module-transport.md` §6

**What is wrong.**

1. **χ² p > 0.01 is a null-hypothesis test used as an equivalence test.** It asks "can I detect *any* difference?", so more histories means it detects the fp32-vs-fp64 differences it exists to tolerate. Adding statistics makes the gate harder — backwards.
2. **Flaky by construction.** Two genuinely identical implementations give p < 0.01 one time in a hundred. `08 §3` then forbids re-running with a new seed without "investigation", so a 1-in-100 outcome burns a session.
3. **"Population series identical under renormalization alignment" is impossible.** `05 §6` even argues it is *exact* "since E3 arithmetic is generation-discrete" — but E3 is driven by `k` from an MC eigen solve, so k differs by ~σ, and `N_n = Π k_i` compounds that over ~500 generations.

**Why it matters.** G0c licenses the GPU backend, which ADR-009 makes the default. A gate that is both flaky and unachievable gets quietly weakened by whichever session hits it.

**Fix.**

> 2. Pass iff **all**:
>    a. `|k_ref − k_gpu| ≤ 3·√(σ_ref² + σ_gpu²)` **and** `|k_ref − k_gpu| ≤ 100 pcm` (absolute equivalence bound, so more statistics cannot tighten the gate);
>    b. shell-resolved fission source by **equivalence**, not χ²: per shell, `|f_ref − f_gpu| ≤ max(3·√(σ_ref²+σ_gpu²), 0.02·f_ref)`;
>    c. population series **statistically**: `|log₁₀N_ref(n) − log₁₀N_gpu(n)| ≤ 3·n·σ_k/(k·ln10)` for all n. Bit-identity across backends is NOT required and MUST NOT be claimed.
> 3. G0c runs a fixed 3-seed set from `gates.toml`; all three must pass.

Delete "(exact, since E3 arithmetic is generation-discrete)" from `05 §6`.

### MAJ-18 — G3 is circular: the parameter it tests is calibrated so that it passes

### MAJ-31 — Isotropic-in-lab scattering with hand-curated 4-group data will not reach ±500 pcm on Godiva/Jezebel

**File/section:** `01-physics.md` §2 E1c; `03-data-contracts.md` §2; `02-architecture.md` D4; `13-risks.md` R-1, R-4; `07-milestones.md` M1-T4

**What is wrong.** The transport model assumes isotropic-in-lab elastic scattering. For fast neutrons on heavy nuclei this is a poor approximation: MeV-range elastic scattering off U and Pu is strongly forward-peaked (diffraction), so the true mean scattering cosine μ̄ is a few tenths, not ~2/(3A) ≈ 0.003. Neglecting it inflates the effective transport cross section, suppresses leakage, and biases k **high** — and Godiva and Jezebel are leakage-dominated bare spheres, i.e. the systems most sensitive to exactly this term.

Meanwhile the gate demands agreement within ±500 pcm (0.5 % in k) against benchmarks whose own evaluated uncertainty is 100–200 pcm, using 4 groups whose values M1-T4 must "curate" without an ENDF pipeline (D4 forbids one; `tools/xs_prep` is optional/future). The only reliable way to hit 500 pcm with 4 groups is to collapse the group constants with a weighting spectrum taken from the problem itself — legitimate practice, but the spec neither describes it nor provides the tooling, and R-2 explicitly forbids tuning XS to hit a target.

So M1-T4 is asked to produce cited constants that pass a tolerance that curation-from-plots cannot reach, while being forbidden from the one technique that would reach it.

**Why it matters.** G0a/G0b are the M1 milestone gate. R-1 is rated M/H with the mitigation "add groups" — but adding groups does not fix anisotropy, and R-4 (which does cover anisotropy) is rated M/M with mitigation "documented limitation; gates empirically bound the bias". That reasoning is circular: the gates are what the bias will break.

**Fix.**

1. Add transport correction to the data contract — `03-data-contracts.md` §2, per isotope per group:
   ```json
   "mu_bar": [0.28, 0.24, 0.20, 0.15],   // mean scattering cosine, lab frame
   ```
   and to `01-physics.md` §2: *"Scattering uses the **transport-corrected P0** approximation: `Σ_tr = Σ_t − μ̄·Σ_s` is used in place of Σ_t for flight sampling, with isotropic-in-lab angular sampling retained. `mu_bar` is REQUIRED in xs sets from schema v2; v1 sets without it are rejected for gate runs."*
2. Re-rate the risks: **R-1 → L = H, I = H**; **R-4 → L = H, I = H**, mitigation *"transport-corrected P0 (μ̄) added in schema v2 before G0a is attempted; if the residual after correction exceeds 500 pcm, the group structure is refined to 6–8 groups (ADR) before the tolerance is relaxed."*
3. Add a fallback path to `08-validation.md` so the project cannot deadlock: *"If, after transport correction and one group-structure refinement, |k − benchmark| remains in (500, 1500] pcm, G0a/G0b MAY be claimed as **CONDITIONAL** with the deviation recorded, provided (a) the sign and magnitude are consistent between Godiva and Jezebel, and (b) all downstream gates that depend on absolute k (G1a, G1b) switch to their ratio-based criteria. A CONDITIONAL gate is recorded as such in `PROGRESS.md` and blocks M6/M7 claims until resolved."*
4. M1-T4a DoD addition: *"document the weighting spectrum used for group collapse and the resulting μ̄ per group; state explicitly that no constant was adjusted to move k toward the benchmark (R-2)."*

### MAJ-21 — `t mod (M·g) == 0` on an accumulated double will essentially never fire

**File/section:** `02-architecture.md` §3

**What is wrong.** The main loop tests `if t mod (M·g) == 0 or hydro_updated` and `if t mod hydro_dt == 0`, where `t` is accumulated by repeated `t += g` in floating point. After a few additions `t` is not an exact multiple of anything; `fmod(t, M*g) == 0` is false essentially always.

### MAJ-20 — The eigen refresh fires every generation, contradicting the interval, the example, and the perf budget

**File/section:** `03-data-contracts.md` §4 (`[kinetics] eigen_refresh_gens = 10`, `[hydro] dt_s = 1.0e-8`) vs `01-physics.md` §4, `02-architecture.md` §3, `03 §5` example, `08 §2` G4

### MAJ-56 — The Philox known-answer test references a vector that does not exist in that form, and seed→key/counter mapping is unspecified

**File/section:** `04-module-core.md` §2; `07-milestones.md` M0-T4

**What is wrong.** Three gaps in one small API.

1. **The KAT.** *"first 16 outputs of `Philox::make(0,0)` MUST match the reference Philox4x32-10 test vector"*. The published Random123 KAT set gives single-block outputs for specific (counter, key) pairs — all-zeros, all-0xffffffff, and a digits-of-π pattern. There is no published "first 16 outputs of seed 0, stream 0" sequence, because "first 16 outputs" depends on how *this* implementation walks the counter, which is exactly what the spec has not defined.
2. **seed/stream → key/counter.** `Philox` has a 128-bit counter and a 64-bit key; `make(uint64_t seed, uint64_t stream)` supplies 128 bits of input. The spec never says which goes where. Every choice is defensible; none is stated; two backends that choose differently break G0c on day one.
3. **Sub-block cursor.** `Stream::uniform()` *"consumes counter block lazily"* — a Philox block yields 4×u32, so the resumable state is (counter, index-within-block). `uint64_t counter() const; // for checkpoint` captures only the first. Resuming mid-block replays up to 3 values, so `03 §8`'s bit-identical resume fails in the general case.

**Why it matters.** M0-T4 is the fourth task and the KAT is its entire DoD. All three gaps also feed BLK-11 and D9.

**Fix.** `04-module-core.md` §2 — make the mapping and the KAT normative:

> **Counter/key layout (normative).** `key = {lo32(seed), hi32(seed)}`. `counter = {lo32(ctr), hi32(ctr), lo32(stream), hi32(stream)}` where `ctr` is the per-stream block index. `Stream` state is the pair `(ctr, sub)` with `sub ∈ [0,4)`; `uniform()` returns `(block[sub] >> 8) * 0x1.0p-24f` and advances `sub`, incrementing `ctr` and refilling on wrap.
>
> **Known-answer tests (normative).** (a) The three published Random123 Philox4x32-10 single-block vectors (counter/key all-zero; all-0xffffffff; the π pattern) MUST reproduce exactly — these are the portability check. (b) A **project-local** vector: the first 16 `uniform()` values of `Stream(seed=0, stream=0)` are recorded in `tests/unit/rng_kat.inl` when M0-T4 lands and are frozen thereafter; changing them requires an ADR. This is the regression check.
>
> **Checkpoint.** `Stream::state()` returns `(ctr, sub)`; both are serialized (`03 §8` section 2). Restoring `(ctr, sub)` reproduces the exact remaining sequence.

Also resolve the precision mismatch (MIN-13): `uniform()` returning `float` contradicts `01 §9`'s "IEEE double everywhere" for `ref/`. Provide both `float uniform_f()` and `double uniform_d()`, and state that `ref/` uses the double form.

### MAJ-39 — Warnings-as-errors has no third-party carve-out, and the CMake 4 / vcpkg / CUDA 13 combination has known first-build failure modes

**File/section:** `02-architecture.md` §4; `12-deployment.md` §1, §2; `07-milestones.md` M0-T2

**What is wrong.** `02 §4` mandates `-Wall -Wextra -Werror` / `/W4 /WX` project-wide with no exemption. On this exact toolchain that interacts badly with three things the spec pins:

1. **CUDA headers under `/W4 /WX`.** CUDA runtime and Thrust headers emit warnings at `/W4`; with `/WX` the first `#include <cuda_runtime.h>` fails the build. `nvcc` also does not accept host warning flags directly — they must be routed through `-Xcompiler`, which CMake does only if the flags are attached as `CUDA` language options rather than blanket `add_compile_options`.
2. **CMake 4.x removed long-deprecated compatibility.** `cmake_minimum_required(VERSION <3.5)` is a hard error in CMake 4, and a number of vcpkg ports still declare old minimums. The standard workaround is `-DCMAKE_POLICY_VERSION_MINIMUM=3.5` in the preset's cache variables. `12 §1` pins CMake **4.3.3** and says "≥ 3.28 required" without mentioning this. **UNCERTAIN** which specific ports in this dependency set are affected — the point is that the mitigation is not documented, not that a particular port is known-broken.
3. **vcpkg manifest reproducibility.** `12 §1` says "pinned versions in `vcpkg.json`" and lists port *names* only. Manifest mode is reproducible only with a `builtin-baseline` commit SHA (plus optional `overrides`). Without it, two sessions weeks apart resolve different versions and `03 §6`'s `code_version`/provenance story silently breaks.

**Why it matters.** M0-T2 is the second task; a failing first build is the worst possible first experience for the multi-session protocol, and the "green-state rule" then blocks every subsequent claim.

**Fix.** `02 §4` →

> **Warnings.** `-Wall -Wextra -Werror` (MSVC `/W4 /WX`) apply to **first-party targets only**, set per-target via `target_compile_options`, never globally. Third-party headers are consumed via `SYSTEM` includes; vcpkg targets are linked as imported targets. CUDA host flags are attached to the `CUDA` language and routed with `-Xcompiler`; device-side warnings use `-Werror all-warnings` only on first-party `.cu` files.

`12 §1` additions:

> - `vcpkg.json` MUST declare a `builtin-baseline` commit SHA; the SHA in use is recorded here and changing it requires an ADR.
> - Presets set `CMAKE_POLICY_VERSION_MINIMUM=3.5` in `cacheVariables` to keep CMake 4.x compatible with ports declaring pre-3.5 minimums.
> - Presets set `VCPKG_ROOT=C:\vcpkg` and `CMAKE_CUDA_ARCHITECTURES=89;80;90` with `89-real;80-virtual;90-virtual` for the PTX-forward-compat policy in `05 §6`.

### MAJ-32 — The eigen batch is too small to saturate the GPU and marginal for σ ≤ 25 pcm; 10 inactive generations is too few

**File/section:** `01-physics.md` §3; `03-data-contracts.md` §4 `[eigen]`; `appendix/constants.md` C-900; `08-validation.md` §2

**What is wrong.** Gate runs use `batch = 1e5`, `inactive = 10`, `active = 50`. Three problems.

1. **GPU utilisation.** 1e5 particles across an RTX 4070 Ti SUPER (8448 CUDA cores, ~66k resident threads at full occupancy) gives under 2 particles per resident thread. After the first few supersteps the queues shrink further, so most of each generation runs at low occupancy with a full global sync at every generation boundary. GPU MC codes typically use 1e6–1e7 per batch for this reason. The spec never discusses batch size as a GPU-efficiency parameter — only as a statistics parameter.
2. **σ ≤ 25 pcm is marginal.** 1e5×50 = 5e6 active histories. For bare fast metal spheres this lands around 20–30 pcm depending on the estimator and the inter-cycle correlation — i.e. the gate threshold sits inside the run-to-run spread of the σ estimate itself. **UNCERTAIN** at the ±10 pcm level (I have not run this code); the point is that the spec asserts 25 pcm without a supporting estimate, so the first gate run may fail on statistics with no recorded expectation to compare against.
3. **10 inactive generations is too few**, and 50 active is too few for a trustworthy σ. The standard-error-over-active-cycles estimator is biased low by inter-cycle correlation, and with 50 cycles the σ estimate itself carries ~10 % relative uncertainty (χ², 49 dof). Combined with BLK-10 (the entropy test being degenerate), nothing detects an unconverged source.

**Why it matters.** These three numbers set whether G0a/G0b are achievable, how long they take, and whether the σ they report means anything.

**Fix.** Separate the *gate* configuration from the *interactive* configuration, and raise both.

`08-validation.md` §2 G0a/G0b step 1 →

> Run eigen with `batch ≥ 1e6`, `inactive ≥ 50`, `active ≥ 200` (C-900). Report σ from the active-cycle standard error **and** from a batched-means estimator over 10 batches of 20 cycles; the gate uses the **larger** of the two, which absorbs inter-cycle correlation.

`appendix/constants.md` C-900 → `1e6 / 50 / 200` for gates; add C-900b `1e5 / 10 / 30` for interactive studio refreshes, with a note that interactive values are NOT valid for gate claims.

Add to `05-module-transport.md` §6: *"Batch size is a GPU-efficiency parameter as well as a statistics parameter: the GPU backend targets ≥ 1e6 in-flight particles at the start of each generation, and M4-T4 records the measured particles/s as a function of batch size in `artifacts/perf_history.jsonl`."*

### MAJ-33 — Double-precision tallies run at 1/64 rate on the dev GPU; the spec's precision policy does not mention it

**File/section:** `01-physics.md` §9; `05-module-transport.md` §6 ("Tallies in double via block-shared reductions"); `12-deployment.md` §1a

**What is wrong.** The precision policy is *"`gpu/`: float for positions/directions, **double** for population/energy tallies"*. On GeForce Ada (sm_89) FP64 throughput is 1/64 of FP32 — roughly 0.7 TFLOPS against ~44. If tally accumulation happens per collision in double, it can dominate a kernel that is otherwise FP32-bound.

This is specifically a *dev-machine* hazard. The H200 cloud target has full-rate FP64 (~34 TFLOPS), so the same code profiles completely differently on the two targets the spec cares about — and G4 is measured on the dev GPU.

**Why it matters.** M4-T4's perf pass is "Nsight profile, coalescing, eigen batch tuning". Coalescing is the listed suspect; FP64 throughput is the unlisted one, and it is the one that differs 50× between the two deployment targets.

**Fix.** `01-physics.md` §9 →

> - `gpu/`: float for positions/directions and per-event arithmetic. Tallies are accumulated in **fixed-point integer** (int64 with a documented scale factor) or in float within a block, then promoted to double **once per block per generation** in the final reduction. Per-collision double arithmetic is forbidden: on the dev GPU (sm_89, GeForce Ada) FP64 runs at 1/64 rate, whereas on the H200 cloud target it runs at full rate — so a design that is fast on one is slow on the other. Fixed-point block accumulation also makes the reduction exactly associative, which BLK-11 requires.

Add to M4-T4's DoD: *"Nsight report includes the FP64 instruction fraction; if it exceeds 1 % of issued instructions, record the reason in SESSIONS.md."*

**File/section:** `03-data-contracts.md` §8; `02-architecture.md` D9; `07-milestones.md` M5-T1; `13-risks.md` R-7

**What is wrong.** Four defects.

1. **Precision loss.** Section 3 is *"Neutron bank (SoA: pos **f32**×3, dir f32×2-encoded, group u8, weight **f32**)"*. But `ref/` is *"IEEE double everywhere"* (`01 §9`). Checkpointing a double-precision CPU bank through f32 fields loses ~29 bits per component, so a `ref/` resume **cannot** be bit-identical — which is exactly M5-T1's DoD.
2. **No identity.** The 64-byte header carries magic, `schema_version`, and byte counts. It does not carry the scenario hash, the data hashes, the code version, or the git hash. Resuming a checkpoint against a different scenario or a rebuilt binary silently produces garbage that looks like a successful resume.
3. **No integrity or endianness.** No per-section CRC, no endianness marker. A truncated checkpoint from a preempted spot instance — the exact scenario D9 exists for — is indistinguishable from a good one.
4. **Missing state.** The listed sections omit the current `EigenResult` (k, Λ, and the fission source that E5 deposition needs), the peak-tracking state that BLK-03's quench criterion requires, and the Philox sub-block cursor (MAJ-56).

**Why it matters.** D9 is a *hard* requirement and the entire cloud strategy (`12 §4`: "spot/preemptible instances are the default assumption") rests on it. R-7 rates checkpoint rot M/M with mitigation "schema_version per section", which addresses none of the four.

**Fix.** `03-data-contracts.md` §8 →

> **Header (128 B):** magic `NSCKPT02`, `schema_version`, endianness marker, `backend` (`ref`|`gpu`), `bank_precision` (`f32`|`f64`), `scenario_sha256`, `data_sha256`, `code_version`, `git_hash`, section table (offset, length, CRC32 per section).
>
> **Load rules.** A checkpoint MUST be rejected with a precise diagnostic if magic, `schema_version`, endianness, `scenario_sha256`, `data_sha256`, or `git_hash` differ from the current run, or if any section CRC fails. Old checkpoints are never required to load (R-7), but a mismatched one MUST NOT load silently.
>
> **Sections:** 1 `SimClock` (phase, t, generation index n, exponent offset, F_peak, supercritical_reached) · 2 RNG (Philox key + `(ctr, sub)` per stream) · 3 Neutron bank, **at the backend's native precision** (`bank_precision` declares which; `ref/` writes f64) · 4 Geometry state · 5 Hydro state (tier-specific, versioned per tier) · 6 Latest `EigenResult` (k, Λ, σ, fission source) · 7 Tally accumulators (f64 or fixed-point, per `01 §9`) · 8 Sweep cursor (nukefarm only).

Re-rate R-7 to L = M, I = **H**, mitigation *"identity fields + per-section CRC + native-precision bank; T-resume at every phase boundary and mid-eigen"*.

### MAJ-42 — Golden tests are backend-dependent but treated as absolute hashes

**File/section:** `11-testing.md` §1 (Golden), §3 (CI matrix); `12-deployment.md` §2

**What is wrong.** Golden tests hash "canonical scenario artifacts (`tally.json`, gate reports, cinema test frames)". But ADR-009 makes `--backend gpu` the default, and `01 §9` guarantees identity only *within* a backend. So a `tally.json` hash generated on GPU will not match one generated by `ref/`, and vice versa.

Meanwhile `11 §3` runs golden tests on `windows-latest` and a `linux container` — both CPU-only runners — while `12 §2` states *"A CPU-only machine MUST build `nscore`, `nukebench`, `nukefarm`, and run unit/**golden** tests."* If the goldens were generated on the dev GPU, every CPU-only run fails; if generated on CPU, the GPU default never matches them.

**Why it matters.** Golden tests are the project's regression net across dozens of sessions. A net that fails on every second machine gets disabled, and then nothing catches silent numeric drift.

**Fix.** `11-testing.md` §1 →

> **Golden.** Goldens are recorded **per backend**: `tests/golden/<artifact>.<backend>.sha256`. A golden test compares against the golden for the backend under test and SKIPs (not FAILs) if no golden exists for that backend. Additionally, `tally.json` goldens are compared **structurally** — every field present, all six `03 §5` invariants hold, and every floating value within a declared relative tolerance (`1e-12` same-backend, `3σ` cross-backend) — so a physics regression is caught even where an exact hash is meaningless. Cinema frame goldens are perceptual-hash comparisons with a declared threshold, never exact hashes (denoiser and driver versions change).

Adjust `12 §2` to *"…and run unit and CPU-backend golden tests"*.

## 2.5 Multi-session process design

### MAJ-40 — The protocol has no dependency graph, no impact analysis, and no unique session identity

**File/section:** `README.md` §5, §6, §7; `PROGRESS.md` (task table)

**What is wrong.** Four independent gaps in the coordination model, all of which bite specifically when sessions run in parallel — which ADR-009 explicitly encourages ("M4-T1/T2 run in parallel with M2/M3").

1. **No dependency graph.** `PROGRESS.md`'s task table has ID / status / claimed_by / claimed_at / notes. Task ordering lives in prose — `07`'s "tasks are ordered", the ADR-009 retime note, and scattered "requires X" statements. A fresh session cannot compute what is *runnable*; it can only see what is `todo`. The M4 note is the clearest case: "M4-T1 SHOULD start immediately after M1-T1" is discoverable only by reading a blockquote inside a milestone table.
2. **Non-unique session ids.** §5.3 says *"use `session-YYYY-MM-DD-<letter>` if you have no stable id"*. Two sessions starting the same day both reach for `-a`. There is no allocation rule (e.g. "scan `SESSIONS.md` for the highest letter used today and take the next").
3. **Claim races need a human.** §7 says *"`PROGRESS.md` conflicts: keep both task rows, **human resolves** the `NEXT ACTION` line"* — in a system whose premise is dozens of autonomous sessions. And the claim is a plain-file edit with no atomicity: both sessions read `todo`, both write `in_progress`, both proceed.
4. **No amendment impact analysis.** §6 describes *how* to amend (edit + CHANGELOG + ADR) but never says *where else to look*. MAJ-04 and MAJ-05 are the direct evidence: ADR-009 changed the GPU baseline and the CUDA version, and both facts survive uncorrected in files the amending session did not think to open.

**Why it matters.** These are the failure modes the whole protocol exists to prevent, and they are the ones it does not cover.

**Fix.** Four edits.

1. **Dependency column.** Add `depends_on` to `PROGRESS.md`'s task table and populate it from `07` (e.g. `M4-T1 | todo | — | — | M1-T1 | gpu buffers + device Philox`). Add to `README.md` §5: *"A task is **runnable** iff its status is `todo` and every task in `depends_on` is `done`. Claim only runnable tasks. If you believe a dependency is wrong, fix `depends_on` and log a CHANGELOG line — do not work around it."*
2. **Session id allocation.** §5.3 → *"Your session id is `session-YYYY-MM-DD-<letter>`. Scan `SESSIONS.md` for entries with today's date and take the next unused letter. If you find your chosen letter already present when you write your END entry, re-letter your entry and note the collision — it means a parallel session was running."*
3. **Claim protocol with a tiebreak that does not need a human.** §7 →
   > The claim is the `PROGRESS.md` edit **plus** an empty commit `claim: Mx-Ty by <session-id>` pushed before work begins. If two claims for the same task exist, the one with the **earlier commit timestamp** wins; the later session MUST abandon the task, revert its claim row, and pick another runnable task. Ties (identical timestamps) are broken by lexicographic session id. No human is required.
4. **Impact analysis.** §6 → *"Before completing an amendment: grep the entire spec for the fact you changed (device name, version pin, threshold value, field name, identifier) and update every occurrence. The CHANGELOG line MUST list every file touched. An amendment that changes a fact in fewer files than the fact appears in is incomplete and MUST be treated as a defect by the next session that notices."*

### MAJ-41 — Nothing survives a compacted or crashed session mid-task

**File/section:** `README.md` §5 (END protocol), §8 (context discipline); `SESSIONS.md`

**What is wrong.** The protocol captures state only at two points: the claim (START) and the handoff (END). §8 says *"Running low on context mid-task? Stop early and execute the END protocol"* — which assumes the session **notices**. Context compaction is often automatic and silent; a crash gives no warning at all. Everything between claim and END is lost: what was tried, what failed, what the half-written code assumes, which of three candidate approaches was rejected and why.

The verify-first rule (§4) recovers *whether* the claimed state is real. It does not recover *what the session had figured out*.

**Why it matters.** The most expensive thing a session produces is not code — it is the understanding of why the obvious approach does not work. On a project with this many subtle physics traps (BLK-03, BLK-04, MAJ-31), rediscovering that repeatedly is the dominant cost.

**Fix.** Add an in-task journal to `README.md` §5:

> ### DURING (continued)
> 4b. **Keep a running journal.** Create `spec/wip/<session-id>-<task-id>.md` at claim time and append to it as you go — one line per non-obvious finding, dead end, or assumption. Append **before** you act on the finding, not after. This file is disposable and never merged into the spec.
> 4c. At END, fold the durable items into your `SESSIONS.md` entry's "Notes for next session" and delete the WIP file. If you find an **orphaned** WIP file (its task is not `in_progress` by you, or its claim is > 24 h old), read it first — a session died holding it — then fold anything useful into your own notes and delete it.

and to §4 (verify-first): *"Check `spec/wip/` for orphaned journals before starting. An orphan is evidence that the claimed state in `PROGRESS.md` is mid-flight, not finished."*

Add `spec/wip/` to the repo tree in `02 §2` with a `.gitignore` exception so journals are committed (they are only useful if the *next* session can see them).

### MAJ-22 — The anti-seed-shopping guard is unenforceable, and gate seeds are not normative

**File/section:** `08-validation.md` §3; `06-frontends.md` §1

**What is wrong.** The guard is *"Re-running a gate with a different seed that fails requires investigation before claiming passage (no seed-shopping; record all attempts in the gate report directory)"*. It is an honour-system rule with three holes:

1. **The seed is free.** Nothing fixes which seed a gate uses, so a session need not "re-run with a different seed" — it can simply run once with a seed that works. There is nothing to record.
2. **The evidence is self-written.** `gate_report.json` is produced by the same session that claims the gate, has no schema (MAJ-23), and is verified by nobody.
3. **"Record all attempts" has no mechanism.** Attempts are files in a directory the session controls; deleting one leaves no trace.

**Why it matters.** `08 §3` says *"a gate passes only via `nukebench gate` exit code 0 — not by inspection"*, and `README.md` §4 says *"trust gates, not prose"*. The gate is the root of trust for the entire multi-session protocol, and its integrity currently rests on the good behaviour of the session being checked.

**Fix.** Make the seed set part of the gate definition, so seed-shopping is not a thing that can be done.

1. `08-validation.md` §3 →
   > - Every gate has a **normative seed set** in `data/benchmarks/gates.toml` (default `[1, 2, 3, 4, 5]`). `nukebench gate` runs **all** seeds in the set and exits 0 only if the pass criterion holds for **every** seed. `--seed` is not accepted by `nukebench gate`; supplying it is a usage error (exit 2).
   > - `gate_report.json` records every seed's result, the gates.toml sha256, the scenario and data hashes, the git hash, backend and device. It is written **atomically** and is append-only per gate: a re-run appends a new attempt block rather than replacing the file.
   > - Changing a gate's seed set requires an ADR, exactly as changing a threshold does.
2. `06-frontends.md` §1 — remove any implication that `gate` takes a seed; add `nukebench gate --gate G0a --report <path>` only.
3. Add to `11-testing.md` §4: *"a negative test asserts `nukebench gate --seed 7` exits 2."*

This converts an honour-system rule into a mechanical impossibility, which is what a root of trust needs.

### MAJ-44 — `canonical_hash()`'s "normalized TOML" is undefined, so provenance and sweep dedup silently diverge

**File/section:** `04-module-core.md` §6; `03-data-contracts.md` §6, §7; `07-milestones.md` M5-T2

**What is wrong.** `Scenario::canonical_hash()` is *"sha256 of normalized TOML"*. "Normalized" is defined nowhere. Every ambiguity changes the hash: key ordering, table ordering, float formatting (`4.585` vs `4.5850` vs `4.585e0`), whether comments are stripped, whether defaults are materialised before hashing, line endings (CRLF on the dev machine, LF in the container), and whether the `[data]` files are included (BLK-08).

**Why it matters.** The hash is load-bearing in three places: `run.json`'s `scenario_sha256` (provenance), M5-T2's *"rerun dedup by scenario hash"*, and checkpoint identity (MAJ-34). Two sessions — or the dev machine and the container — computing different hashes for the same scenario means the sweep re-runs everything and the dedup silently does nothing. On a 5000-run cloud sweep that is a direct cost.

**Fix.** `04-module-core.md` §6 →

> **`canonical_hash()` (normative).** (1) Load the scenario and materialise **all** schema defaults. (2) Serialise to a canonical form: keys sorted lexicographically at every level; tables emitted before arrays-of-tables; no comments; LF line endings; UTF-8 without BOM; integers as decimal without separators; floats via shortest round-trip decimal (`std::to_chars` scientific, `%.17g` fallback) so that parse(emit(x)) == x exactly. (3) Concatenate: the canonical scenario bytes, then `sha256` of the resolved xs file, then `sha256` of each resolved material file in `id` order. (4) `sha256` the concatenation.
>
> A round-trip test (`04 §7`) asserts hash stability across: key reordering in the source file, comment changes, CRLF↔LF, and equivalent float spellings.

### MAJ-26 — The cross-section schema leaves five things ambiguous, including what Σ_t is

**File/section:** `03-data-contracts.md` §2; `04-module-core.md` §3

**What is wrong.** Five separate ambiguities, any one of which changes k:

1. **Σ_t is never defined.** The schema gives `sigma_f`, `sigma_a`, `sigma_s` and no total. E1a samples flight against `Σ_t,g`; E1c samples reactions "from group XS shares". Is `Σ_t = Σ_f + Σ_a + Σ_s` or `Σ_a + Σ_s` (with Σ_a including fission)? Both are common conventions.
2. **Is `sigma_a` capture-only or capture-plus-fission?** The example (`sigma_f: 1.95`, `sigma_a: 0.12`) implies capture-only, since 0.12 b is far too small for total absorption in fast Pu. But `sigma_a` conventionally means *absorption* = capture + fission. Read conventionally, E1c's reaction sampling double-counts fission.
3. **Group ordering is unstated.** `group_bounds_MeV: [20.0, 3.0, 1.0, 0.1, 1e-5]` is descending, implying group 1 = highest energy, but nothing says so, and nothing says whether `group` (the `u8` in the SoA and checkpoint) is 0- or 1-based.
4. **The transfer matrix has no orientation or normalisation.** `transfer` is "optional n_groups×n_groups downscatter matrix". Is `T[i][j]` from-i-to-j or to-i-from-j? Does each row sum to 1 (a probability matrix) or to `sigma_s` (a cross-section matrix)? Is upscatter permitted (the name says "downscatter" but the shape is full)?
5. **`Mat4` is undefined.** `04 §3` declares `std::optional<Mat4> transfer`. `Mat4` conventionally means a 4×4 *float* matrix from a graphics library; here it must be 4×4 double, and its index convention is item 4.

Two further gaps worth noting: `transfer: null` means "within-group only", i.e. **no slowing-down at all** — with a fission spectrum χ that puts 55 % of neutrons in group 1 and no downscatter, the problem is effectively one-group with a fixed spectrum, which cannot represent the U-238 fission threshold that supplies ~20 % of the yield. And there is no `sigma_n2n`, though (n,2n) on the U-238 tamper and Be initiator is a real fast-system multiplication channel.

**Why it matters.** M0-T5 writes the loader and M1-T2 writes the transport against it. Each ambiguity is a coin flip that changes k by percent-level amounts — against a gate tolerance of 0.5 %.

**Fix.** `03-data-contracts.md` §2, add a normative "Semantics" block:

> **Semantics (normative).** Groups are indexed **0-based**, ordered from **highest to lowest energy**; `group_bounds_MeV` has `n_groups+1` entries in strictly descending order, and group `g` spans `(bounds[g+1], bounds[g]]` MeV.
> `sigma_f` = fission; `sigma_c` = **radiative capture** (field renamed from `sigma_a` to remove the ambiguity — `sigma_a` is rejected by the loader with a migration diagnostic); `sigma_s` = total scattering (elastic + inelastic); `sigma_n2n` = (n,2n), optional, default 0.
> **`sigma_t = sigma_f + sigma_c + sigma_s + sigma_n2n`**, computed by the loader; it MUST NOT appear in the file.
> `mu_bar` = mean lab-frame scattering cosine per group (REQUIRED from schema v2, MAJ-31); transport-corrected total `sigma_tr = sigma_t − mu_bar·sigma_s` is used for flight sampling.
> `transfer[from][to]` is the **probability** that a scattering event in group `from` places the neutron in group `to`; each row MUST sum to 1.0 ± 1e-6. `null` ⇒ identity (within-group scattering only) and is permitted **only** for `status = "SIM"` test sets — a gate run with `transfer: null` is rejected.
> Upscatter (`to < from`) MUST be zero in v1; the loader rejects non-zero upscatter.
> All cross sections in **barns**.

`04-module-core.md` §3: replace `std::optional<Mat4>` with `std::optional<std::array<std::array<double,4>,4>> transfer; // [from][to]` and add `float mu_bar; float sigma_c; float sigma_n2n;` to `GroupData`.

### MAJ-25 — The `ui_range` annotation convention is ambiguous, inconsistently named, and unit-mismatched

**File/section:** `03-data-contracts.md` §4; `10-ui.md` table; `06-frontends.md` §3

**What is wrong.** Three problems in the mechanism `10 §intro` and `06 §3` both say drives widget generation.

1. **No mapping rule.** Three different naming styles appear in one example: bare `ui_range` (in `[initiator]`, which has *three* numeric fields — which one does it annotate?), `ui_range_ratio` (in `[compression]`, suffixed with the field name), `ui_range_batch`, `ui_range_jitter`. Nothing states the rule.
2. **Unit mismatch.** `10-ui.md` gives "Generation time | `kinetics.generation_time_s` | Default **10** | Range **1–100** | **ns**". The schema field is in **seconds** (`1.0e-8`). A generator reading `ui_range` from the scenario would produce a slider from 1 to 100 **seconds**. The same mismatch affects the initiator (n/s vs the table's mixed "0–1e7…1e8") and jitter (the schema uses `jitter_ns`, so that one happens to agree).

**Fix.** Replace the bare-`ui_range` convention with a single explicit annotation table per section. `03-data-contracts.md` §4:

> **UI annotations (normative).** Each parameter's UI metadata lives in a `[ui.<dotted.path>]` table, never inline:
> ```toml
> [ui."kinetics.generation_time_s"]
> label  = "Generation time"
> range  = [1.0e-9, 1.0e-7]      # ALWAYS in the field's own schema units
> display_unit = "ns"            # UI multiplies by 1e9 for display only
> display_scale = 1.0e9

### MAJ-43 — `tally.json` reports a single `k_eff` for a time-varying run, and no uncertainty on the gated quantities

**File/section:** `03-data-contracts.md` §5; `08-validation.md` §2 G2, G3

### MAJ-35 — The sweep boundary constrains the objective's *label*, not its *search space*

**File/section:** `00-overview.md` §3.4; `02-architecture.md` D8; `DECISIONS.md` ADR-007; `03-data-contracts.md` §7

**What is wrong.** `00 §3.4` states that batch objectives are "calibration/sensitivity only", and ADR-007 makes `objective.kind ∈ {sensitivity, calibrate}` schema-enforced. But `kind` is a *label on the objective function*. The **search space** is unconstrained. `03 §7`'s own example declares:

```toml
[objective] kind = "calibrate"
            target_yield_kt = [18.6, 24.8]
[[space]]   param = "lenses.jitter_ns"        range = [0.0, 1000.0]
[[space]]   param = "compression.ratio"       range = [1.0, 3.0]
[[space]]   param = "tamper_override.material" values = ["u_natural","tungsten","beryllium"]
```

An MCTS sampler with a 5000-run budget, searching over tamper material and compression ratio, scored on proximity to a target yield, is a design-optimisation loop. Changing `kind` to `"sensitivity"` would not change a single run it performs. The constraint is not enforceable as written — which is exactly what dimension G asks about.

`10-ui.md`'s ranges compound it: pit radius 3–6 cm (≈2.5–14 kg of Pu), tamper thickness 0–12 cm, tamper material U/W/Be/none, lens count 12–92. Single-point interactive exploration of those is defensible education (it is what Wellerstein's public simulator does). **Automated search over the same space against a yield objective is a different activity**, and the spec's own §3.4 is aimed at the second while its schema only regulates the first.

**Why it matters.** This is the one boundary in `00 §3` that a session could cross while believing it is compliant, because the schema says `calibrate` and the schema is presented as the enforcement mechanism.

**Fix.** Constrain the space, not the label. `03-data-contracts.md` §7:

> **Sweep space restriction (normative).** Every `[[space]]` axis MUST declare `axis_class`:
> - `numerical` — SIM knobs only (batch sizes, tolerances, refresh intervals, seeds). Unrestricted.
> - `uncertainty` — a physical parameter swept **within the published uncertainty of the historical device**. `range` MUST lie inside the `[lo, hi]` band of the referenced constant, and `constant_id` is REQUIRED. Example: tamper mass over 108–111 kg (C-103), compression ratio over 2.0–2.5 (C-060).
> - `pedagogical` — a physical parameter swept outside the published envelope, permitted **only** with `sampler = "grid"`, `budget_runs ≤ 100`, and `objective.kind = "sensitivity"`. Optimising samplers (`mcts`, `lhs`, `random`) and `kind = "calibrate"` are **rejected by the loader** when any axis is `pedagogical`.
>
> `objective.kind = "calibrate"` requires **every** axis to be `numerical` or `uncertainty`. This is what makes "calibration only" enforceable: you may fit the model's uncertain inputs to the published yield band, and you may not search device configurations for yield.

`00 §3.4` → *"Batch objectives are calibration/sensitivity only, enforced by the **axis_class** restriction in `03 §7` — the search space, not merely the objective label. Optimising samplers may only search numerical and published-uncertainty axes."*

Update the `03 §7` example so it is compliant (replace the tamper-material axis with a tamper-mass axis over C-103's band), since the example is what a session copies.

# 5. Verdict, top fixes, and what to preserve

## 5.1 Overall verdict

### AMEND-THEN-SHIP

Not MAJOR REWORK. The architecture is sound and, in several places, better than what I would have specified: the two-tier ref/GPU oracle with differential validation, the analytic-tracker-first geometry decision, counter-based RNG chosen *because* resume must be exact, the bands-not-points discipline, and the living-state session protocol are all correct calls that would survive any review. The bones are good.

Not SHIP AS-IS, and not close. Fourteen blockers, of which four are physics errors that change the headline result by factors of order one (BLK-01, BLK-03, BLK-04, BLK-05), four are foundational-task blockers that stop M0 dead (BLK-06 through BLK-09), and one is a protocol defect that would let the spec fork against itself on the very first task (BLK-12). Notably, **three of the four physics errors all push yield in the same direction** (down), which is the signature of a model that will get "fixed" by tuning a compression knob until G2 passes — and G2 as currently written would accept that.

The most important structural observation: **the gate system, which is the entire trust anchor of the multi-session design, is the weakest part of the spec.** G1a rests on a units category error, G1b's threshold sits on top of its own expected value, G2's bands are untraceable and jointly infeasible at the corners, G3 is circular by construction, G4 is self-contradictory and gameable, and G0c is simultaneously flaky and unachievable. `README.md` §4 says "trust gates, not prose" — that is the right instinct, and it makes gate quality the single highest-leverage thing to fix.

Estimated remediation: one focused session for the blockers, plus a second for the gate redesign (MAJ-12 through MAJ-19 should be triaged together — they are one coherent piece of work, not eight independent edits).

## 5.2 Top 5 fixes that must happen before M0-T1 starts

Ordered by *what unblocks the most downstream work*, not by severity.

1. **BLK-12 — Settle the repo root and kill the second spec copy.** One line of decision, but everything else is built on top of it, and it is the only finding that can corrupt the protocol itself rather than the product. Amend `02 §2`, M0-T1, and `PROGRESS.md`'s NEXT ACTION in one commit.

2. **BLK-09 + BLK-06 + BLK-07 + BLK-08 — Make the data layer machine-readable.** These four are one piece of work: extend the constant schema for bands and pending values, add the missing molar masses, fix the `[[layers]]` TOML, fix the initiator range, add the `[data]` table. Together they unblock M0-T3 and M0-T5, which are the two hard-blocked foundation tasks. Nothing downstream can start without them.

3. **BLK-03 + BLK-04 + BLK-01 — Fix the three co-directional yield errors before any gate is calibrated against them.** Quenching at peak power, the fixed generation time, and the Tier-1 formula. These must land *before* M2/M3 rather than after, because once a compression ratio has been tuned to make G2 pass with these errors present, unwinding it means re-deriving every calibration. This is the finding I would most regret deferring.

4. **BLK-05 — Resolve implicit vs analog transport, in both files.** M1-T2 and M1-T3 cannot start, and the two files a session might read disagree, so the failure is silent. Cheap to fix, and the added `k_inf = ν̄Σ_f/Σ_a` unit test catches an entire error class.

5. **MAJ-13 + MAJ-22 — Give every gate threshold a constant ID and a derivation, and make the gate seed set normative.** This is the smallest change with the largest integrity return: it converts the anti-seed-shopping rule from an honour system into a mechanical impossibility, and it makes the "gates may only change via ADR with cited evidence" rule actually enforceable against numbers that currently have no citation at all. Do it before the first gate is written, because retrofitting IDs onto thresholds already embedded in `gates.toml` and gate reports is much harder.

**Deliberately not in the top 5, but do them next:** BLK-14 (ICSBEP — needs an owner decision, so start the conversation now even though the fix is not a spec edit), BLK-11 (GPU determinism — must land before M4-T2 writes the bank), and the gate redesign as a block (MAJ-12/14/15/16/17/18/19).

## 5.3 Preserve — do not let triage "fix" these

Genuinely good, and several are better than standard practice. Whoever triages this report should treat the following as load-bearing and leave them alone.

**Process**

- **The router + living-state design** (`README.md` + `PROGRESS.md` + `SESSIONS.md` + `DECISIONS.md` + `CHANGELOG.md`). The separation of concerns is right: one file for orientation, one for current state, one append-only for history, one append-only for decisions, one for spec deltas. My findings in §2.5 add missing pieces (dependency graph, session-id allocation, WIP journal, impact analysis) — none of them argue against the structure.
- **Verify-first, and "trust gates, not prose"** (`README.md` §4). This is the single best idea in the document. The problem is that the gates are weak, not that the principle is wrong. Strengthen the gates; do not weaken the rule.
- **The green-state rule and the mandatory END protocol** (§5.7–5.9), including "never hand off red" and "exactly one NEXT ACTION". The insistence on a single imperative next action is unusually disciplined and should not be softened into a list.
- **"No session completes the project; every session completes a task and a clean handoff"** (§8). This is the correct framing for the whole enterprise.
- **The amendment protocol's core rule** — code contradicting the spec is a bug; if reality contradicts the spec, amend the spec, don't fork the truth (§6). Keep the sentence verbatim.

**Scope discipline**

- **`00 §3` in its entirety as a concept**, especially §3.5 (keeping Pu burn-up and tamper yield fraction separate) and §3.6 (yield is a range). §3.5 in particular catches the exact conflation the source document explicitly warns about, and the tally schema enforces it structurally with two mandatory separate fields. That is the spec doing its job.
- **Status tags** (`PUBLIC` / `DECLASSIFIED` / `RECONSTRUCTED` / `SIM`) on every constant, propagated into the UI as badges. Worth extending (MAJ-13 adds gate bands to it), never worth removing.
- **`[VERIFY]` placeholder discipline** in `08 §1` and the appendix — marking unresolved values loudly rather than guessing them is exactly right, and it is why BLK-14 is discoverable at all.
- **Bethe–Feynman as a display-only overlay** (`00 §3.3`, `01 §7`), forbidden from feeding simulation state. The right call, cleanly enforced.

**Architecture**

- **D1 — the ref/GPU two-tier design with differential validation.** Correct, and the reason a GPU MC code of this kind is debuggable at all.
- **D2 — analytic sphere tracker first, OptiX only for Stage 3.** Right for the physics (closed-form ray–sphere beats any BVH for nested spheres), right for the cloud (H100/H200 have no RT cores), and right for the schedule (validated neutronics before OptiX debugging). The reasoning is stated well enough that a future session will not be tempted to "modernise" it.
- **D9 + ADR-008 — Philox chosen specifically because counter-based RNG makes resume exact.** The rationale is recorded, which is what makes it durable. BLK-11 says the *implementation sketch* defeats it; the decision itself is correct.
- **D7 — one library, four frontends, zero physics in `src/app/`,** with "any physics logic found in `src/app/` is a defect" as the consequence. Crisp and testable.
- **The event-based GPU design** (SoA, prefix-sum partition, branchless per-event kernels) is the right architecture and matches the published precedents the research doc cites.

**Physics that is correct and should not be "corrected"**

- **E3a's per-generation bookkeeping is right.** `F_n = k·N_n/ν̄` follows correctly from `N_{n+1} = ν̄·F_n = k·N_n`; the fissions-per-generation accounting is self-consistent with the population update and with `F_cum`. Its only defect is the missing source term (see below) — the k/ν̄ relation itself is correct and should be left exactly as written.
- **E2a power iteration**, `k_{i+1} = F_{i+1}/(F_i/k_i)`, is the standard and correct 1/k-normalised form.
- **E1a free-flight sampling** (`s = −ln ξ/Σ_t`) and **E1c's stochastic rounding** (`⌊x + ξ⌋` for fractional progeny) are both textbook-correct.
- **The analytic ray–sphere math in `04 §4`** (`t² + 2bt + c = 0`, `b = p·d`, `c = |p|² − R²`) is correct as written.
- **The log-renormalization requirement** (`01 §4`, N > 1e30 → renormalize with an exponent offset, carried into `population_series` as log₁₀) is necessary, correctly specified, and made normative rather than advisory. Exactly right.
- **`Φ_kt ≈ 1.45e23` fissions/kt at 180 MeV** is the standard weapons-effects convention and is the correct choice for E6 (MAJ-11 is about C-042 disagreeing with it, not about C-041 being wrong).
- **The layer geometry table.** I independently reproduced the tamper (110.9 kg vs 108–111) and pusher (128.3 kg vs 128–130) masses from the stated radii and densities. The geometry is sound; only the pit triple is over-constrained (MAJ-28).
- **The VRAM budget** in `12 §1a` checks out (33 B/particle → 0.31 GiB at 1e7; 128 MiB per field frame). Someone did the arithmetic.
- **The spec did NOT inherit the research document's arithmetic error.** The source doc states "with k≈2 a single neutron reaches ~2×10²⁴ fissions in ~56 shakes" — which is wrong by ~26 generations (2⁵⁶ ≈ 7×10¹⁶, not 2×10²⁴; the doc's own "~80 generations" figure elsewhere is the consistent one). The spec quietly uses the correct framing and does not propagate the error. That is good source handling and worth noting explicitly so nobody "restores fidelity" to the research doc here.

**One caveat on the preserve list:** E3a is correct *as a recursion* but is missing the initiator source term. `01 §4` says the initiator "contributes `N_init(t)`" and E3a — labelled "exactly" — has no `S` term. The fix is additive and does not disturb the correct part: `N_{n+1} = k·N_n + S_{n+1}`, with `F_n = k·N_n/ν̄` unchanged. I list this here rather than as a separate finding because the risk is that a triager reads "E3a is correct" and skips the addition.
