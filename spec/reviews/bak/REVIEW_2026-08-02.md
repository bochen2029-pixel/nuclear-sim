## A. Blockers (fix before M0-T1)

These break the earliest tasks the spec asks a cold agent to execute. Any of them will strand M0 or M1.

### A-01 [BLOCKER] Canonical scenario TOML is not valid TOML — parser errors out on the example — `03-data-contracts.md` §4

**What is wrong.** The `[[layers]]` block in the canonical scenario example is malformed:

```toml
[[layers]]                      # center outward; inner boundary of first layer = 0
{ id = "initiator", r_outer_cm = 1.00,  material = "be_po_urchin", status = "DECLASSIFIED" }
{ id = "pit",       r_outer_cm = 4.585, material = "pu_ga_delta",  status = "DECLASSIFIED" }
...
```

A `[[layers]]` header opens one entry in the table-array; the following lines must be `key = value` pairs. A bare inline table `{ ... }` at column 0 is a syntax error. Verified with Python 3.13 `tomllib`: `PARSE ERROR: Invalid statement (at line 5, column 1)`.

**Why it matters.** `11-testing.md` §4 says "every canonical example parses" is a mandatory loader test. M0-T5 DoD requires "canonical example files parse". The example is what M0-T5 tests against and what M2-T1 seeds `trinity_canonical.toml` from. First loader run against the example crashes; every downstream task inherits the mis-shaped mental model.

**Fix.** Replace with one of the two valid forms. Recommended (readable and matches the `Scenario::apply_overrides` "layers[pit].material" path syntax if the loader indexes by `id`):

```toml
[[layers]]
id = "initiator"
r_outer_cm = 1.00
material = "be_po_urchin"
status = "DECLASSIFIED"

[[layers]]
id = "pit"
r_outer_cm = 4.585
material = "pu_ga_delta"
status = "DECLASSIFIED"
# ... one [[layers]] block per layer
```

Then update `04-module-core.md` §6 override-path syntax so `layers[pit].material` is documented as "lookup by `id` field" (not array index).

### A-02 [BLOCKER] `tally.json` example is internally inconsistent by ~10× — yield, fissions_total, and burn-up disagree — `03-data-contracts.md` §5

**What is wrong.** The example shows `yield_kt = 20.4` and `fissions_total = 2.96e23`, but with `C-041` (1.452e23 fissions/kt @ 180 MeV) those imply each other **only** at:

- 2.96e23 fissions → 2.04 kt (not 20.4)
- 20.4 kt → 2.96e**24** fissions (not e23)

Verified: `2.96e23 / 1.452e23 = 2.04`. To get 20.4 kt at 180 MeV/fission you need `2.96e24` fissions.

The burn-up numbers are wrong the same way: `fission_mesh.fissions[pit] = 2.1e23`, but a 6.15 kg pit at 98.95% Pu-239 holds `1.53e25` Pu atoms; 2.1e23 / 1.53e25 = **1.4 %** burn-up, not the `pu_fraction = 0.151` (15.1 %) that appears in the same JSON. Should be `2.1e24` (missing a zero).

**Why it matters.** Golden-test authors (`11-testing.md` §1) and gate scorers (`08-validation.md` §G2) will code against these fields. If they use the example as a reference to derive units (e.g., inferring "yield_kt/fissions_total × 1e23 ≈ constant") they will get the units wrong. The example is normative — the spec says "Examples are canonical — tests parse them verbatim" (`03-data-contracts.md` §preamble).

**Fix.** Correct the example to consistent numbers. One self-consistent set:

```json
"yield_kt": 20.4,
"fissions_total": 2.96e24,
"burnup": { "pu_fraction": 0.151, "u238_tamper_fissions": 5.9e23,
            "tamper_yield_fraction": 0.20 },
"fission_mesh": { "format": "radial_shells",
                  "shells_cm": [0.0, 4.585, 11.43, 23.495],
                  "fissions":  [2.10e24, 5.90e23, 2.70e22] }
```

(Adds pusher boundary and drops one order of magnitude only where required; verify the specific numbers you commit to are self-consistent by construction, not by inspection.)

### A-03 [BLOCKER] `fission_mesh` shells/fissions array-length rule undefined — example already violates any sensible rule — `03-data-contracts.md` §5

**What is wrong.** `shells_cm` has 3 boundary values `[0.0, 4.585, 11.43]`; `fissions` has 3 values. With N boundaries you get N-1 shells, so `fissions` should have length 2 (not 3). The example either (a) is short one boundary (should include 23.495 for the pusher), (b) has a spurious 3rd fission value, or (c) uses a different convention (shell edges vs centers vs open-ended outermost). The spec never states which.

**Why it matters.** Consumers (studio "Fields" panel, cinema, tally validators) will implement three different array-shape assumptions. Regressions will not show up until M7-T1 wiring. Also directly interacts with A-02.

**Fix.** Add a normative sentence to §5:

> `fission_mesh` invariant: `len(fissions) == len(shells_cm) − 1`. `shells_cm` is a strictly increasing array of shell boundaries in cm from center outward; `shells_cm[0]` is the innermost boundary (usually 0) and the last value is the outermost tallied radius. Fissions occurring outside the last shell are tallied to `leaked_fissions` (add field), not silently discarded.

Then rewrite the example so lengths agree.

### A-04 [BLOCKER] Guderley exponent value contradicts its stated γ — physics error — `01-physics.md` §5 (E5, Tier-2), `appendix/constants.md` C-070, `05-module-transport.md` §4

**What is wrong.** The spec asserts `R_s(t) = A·(t_c−t)^α_G` with `α_G = 0.688377` **spherical, γ = 1.4** (Guderley 1942 / Lazarus & Richtmyer 1981). The value 0.688377 is the well-known spherical exponent for **γ = 5/3**, not γ = 1.4. Public tabulations (Lazarus 1981; Ponchaut et al. 2006; Ramsey/Kamm/Bolstad 2012 "Guderley problem revisited") give roughly:

- γ = 5/3 (monoatomic ideal gas / HED plasma): α ≈ 0.68838
- γ = 7/5 = 1.4 (diatomic — air): α ≈ 0.71717
- γ = 3: α ≈ 0.6367

So the number 0.688377 is right *if* the intended EOS is γ = 5/3 — which is in fact what `05-module-transport.md` §4 uses for the internal-pressure term (`P_int = (γ−1)·E_dep/V_shell, γ = 5/3`). The label "γ = 1.4" is the bug, not the number.

**Why it matters.** Trinity/Fat Man internal EOS at the relevant compression is closer to a stiffened Grüneisen than either ideal-gas limit, so the choice is a modelling call — but the choice must be internally consistent. Right now Tier-2 uses α from γ=5/3 (correct for the interior gas), while the appendix and the physics chapter label it γ=1.4 (which would be air/HE-product side). If someone later re-derives from the label they will use the wrong exponent (0.71717) and every Tier-2 compression schedule will shift. This is exactly the kind of unit/label bug that survives to a physically wrong gate outcome.

**Fix.** In all three places (01-physics.md §5, appendix C-070, 05-module-transport.md §4), change the label to "spherical, γ = 5/3" (and cite Lazarus 1981 Table for the specific digit). Add a one-line note that the interior EOS was chosen γ = 5/3 for consistency with the ideal-gas post-deposition state, and that this is a modelling choice within Tier-2 fidelity. If the amendment path prefers γ = 1.4, then α_G must become 0.71717 and C-070 must change with it — do not leave the current mismatch.

### A-06 [BLOCKER] `tools/gen_constants` cannot parse the appendix — many entries have ranges, tildes, or prose in the value column — `appendix/constants.md` §1, `04-module-core.md` §1

**What is wrong.** M0-T3 DoD: "generator fails on missing cite/status; header compiles". But the seed data in the appendix has entries like:

- `C-010` σ_f Pu-239: **`1.7–1.8`** (range)
- `C-020` ν̄ Pu-239: **`2.9 (fast slightly > thermal 2.89)`** (value + prose)
- `C-030` generation time: **`~10`** (approximation marker)
- `C-032` fission MFP: **`~13 (12.7 Pu-239)`** (approx + specific value)
- `C-040` E_f: **`~180 (total ~200)`** (two values)
- `C-050` critical mass: **`~10`** (approx)
- `C-051` initiator output: **`~1 n / 5–10 ns at firing`** (rate window as prose)
- `C-060` compression ratio: **`~2–2.5 ×`** (range)
- `C-090` Pu burn-up: **`15–17`** (range)
- `C-102`: **`(6.15 kg, 3.35% molar Ga, ρ≈15.6, Pu-240 1.0%)`** (compound value packed as text)
- `C-104`: value column contains geometry text `~0.32 cm`

`04-module-core.md` §1: "`inline constexpr double`" — a `double` cannot hold a range, an approximation marker, or "1 n / 5–10 ns at firing".

**Why it matters.** M0-T3 stops the pipeline the moment `gen_constants` runs. Either the generator crashes (fails DoD) or the agent hand-picks a value from each range (silently violating the spec's "no invented values" rule and losing the uncertainty).

The strict file must specify one numeric value plus optional `low`, `high`, `sigma`; the human table adds narrative. `data/constants.toml` (M0-T3 output) is generated from the strict file. Also add to the generator: "if entry has `low` and `high`, emit `_low`/`_high` constants alongside the nominal; unit tests assert `low ≤ value ≤ high`."

Additionally, delete the `~`, `≈`, and range glyphs from the values consumed by the generator (keep them in the human column as `notes`). Add a lint pass that rejects glyphs in the numeric column.

### A-07 [BLOCKER] OptiX environment-variable naming is inconsistent across three deployment sections — build will fail non-deterministically — `12-deployment.md` §1, §2, §5

**What is wrong.** Three different env-var names are given for the SAME OptiX SDK path:

- §1 table row: "CMake locates via `OptiX_ROOT` / `OptiX_INSTALL_DIR` pointing there"
- §2 Build: "OptiX targets only when `OPTIX80_SDK` set"
- §5 Secrets: ".env.example documents required vars (`OPTIX80_SDK`, `S3_*`, ...)"

`OPTIX80_SDK` is a leftover from the pre-ADR-009 assumption of OptiX 8.0; the actual installed SDK is 9.1.0 (`C:\ProgramData\NVIDIA Corporation\OptiX SDK 9.1.0`). Whichever preset gets adopted first will accidentally lock the whole project to one of three names.

**Why it matters.** OptiX-optional builds fail silently (target not enabled) if the wrong env var is set. Agents will spend a session chasing "why doesn't `cmake --preset win-x64` see OptiX" when the answer is "you set the variable the wrong file said to set."

Replace `OPTIX80_SDK` in §2 and §5 with `OPTIX_ROOT`, keep §1's `OptiX_ROOT`/`OptiX_INSTALL_DIR` as the CMake-side alias, and add: "compile-time guard `NUKESIM_WITH_OPTIX` is ON iff `OPTIX_ROOT` resolves to a directory containing `include/optix.h`."

## B. Major (fix before the milestone that first uses them)

These do not block M0-T1 but *will* corrupt a milestone if left. Each is dated to the earliest milestone it damages.

### B-01 [MAJOR] G1a band [0.70, 0.95] is essentially unfailable — validation is theatrical — `08-validation.md` §G1a, `07-milestones.md` M2

**What is wrong.** For the fully-specified layer stack (fixed geometry, fixed materials, fixed 4-group XS after M1-T4), the correct k has one value plus a few-hundred-pcm uncertainty from XS choice — perhaps [0.80, 0.87] on any reasonable curated 4-group set. The gate accepts anything in [0.70, 0.95], a **±14 %** window. A simulator that is factor-of-2 wrong on absorption or leakage will pass. The rationale ("~78 % critical") is a public statement of order-of-magnitude, and the band was written to absorb classified-quantity uncertainty — fine — but then the band lost all discriminative power.

**Why it matters.** M2 is where the whole layered assembly gets validated for the first time. If G1a rubber-stamps anything, XS bugs and geometry bugs propagate silently into M3 (kinetics) and M4 (GPU), where they become G2 failures that are much harder to root-cause.

**Fix.** Two gates, not one:
- **G1a-loose** (existing): k ∈ [0.70, 0.95] — must pass, tied to the "~78 %" public band, cannot fail from classified-value uncertainty.
- **G1a-tight** (new, non-blocking but reported): once the XS set is committed at end of M1-T4, freeze a self-consistency window of ±500 pcm around the M1-T4 committed value on the canonical uncompressed geometry. Any drift from that number in later milestones flags a regression. This does not tie the sim to a classified point — it ties it to *the sim's own past outputs*.

Amend `13-risks.md` R-11 (scope drift) to note: "self-consistency windows are OK because they measure the code, not the device."

### B-02 [MAJOR] G4 perf targets: identical `< 1 s` for RTX 4070 Ti SUPER and H200 — the H200 target is meaningless — `08-validation.md` §G4

**What is wrong.** G4 says "Full-assembly single eigen refresh < 1 s on RTX 4070 Ti SUPER (dev) and < 1 s on H200 (cloud)." H200 is ~5–10× the FP32 throughput of a 4070 Ti SUPER and 9× the memory bandwidth. A target that both must meet either means (a) the dev machine target is loose and the H200 will be idle, or (b) the H200 target is really a floor and does not reflect its actual capability. Either way the number is uninformative.

**Why it matters.** Perf regressions on the H200 will not be detected — nothing in G4 says "H200 must be within 3× of scaled expectation". If the GPU kernel accidentally becomes memory-bound in a way that hurts H200 disproportionately, G4 is green.

**Fix.** Split G4 perf targets per device with realistic per-device numbers:
- 4070 Ti SUPER: eigen < 1 s (batch=1e5, 60 gens); studio ≥ 30 fps at defaults.
- H200: eigen < 250 ms (batch=1e5, 60 gens); throughput ≥ 3× 4070 Ti SUPER on the differential harness.

Add to `13-risks.md` a new row (candidate R-12) about perf regression on H200 vs sm_89 (memory-bandwidth divergence).

### B-03 [MAJOR] `c_a` asymmetry calibration is circular — "calibrated so G3 passes" — `01-physics.md` §5 (asymmetry), `05-module-transport.md` §4, `07-milestones.md` M6-T3 DoD, `appendix/constants.md` C-906

**What is wrong.** M6-T3 DoD says "**c_a recorded in constants.toml as SIM**". §5 asymmetry: "c_a calibrated so G3's monotonic-degradation gate passes." G3 procedure (`08-validation.md`): checks that yield drops as jitter grows. The knob that controls how fast yield drops is c_a. So c_a is tuned until the yield-vs-jitter curve matches the shape that G3 requires — and then the gate is declared passed. This is exactly the anti-pattern that `08-validation.md` §3 forbids ("no seed-shopping") but built into the calibration workflow.

**Why it matters.** G3 becomes a self-fulfilling prophecy — it certifies nothing. Any future amendment to the asymmetry model can be trivially "validated" by re-tuning c_a.

**Fix.** Break the loop by calibrating c_a against an independent public claim, not the gate:

1. Calibrate c_a against the C-072 5 % symmetry tolerance claim: pick c_a so that at the public timing jitter ±10 ns (C-071), the resulting fractional drive-pressure perturbation ε equals the median of the 5 % tolerance band.
2. Then run G3 as a **validation**, not a calibration. If G3 fails at the calibrated c_a, that is a real failure requiring model amendment (add ADR) — not a signal to re-tune.

Amend M6-T3 DoD: "c_a is derived from C-071/C-072 by the formula ε = c_a·σ_t/t_rise, solved at σ_t = 10 ns for ε = 0.05; G3 is then a pass/fail check on the resulting model, not a fit." Add a unit test that regresses c_a against the calibration formula on any change to C-071/C-072.

### B-04 [MAJOR] Anti-seed-shopping guard is honour-based — nothing enforces it — `08-validation.md` §3, `07-milestones.md` all gate DoDs

**What is wrong.** "Re-running a gate with a different seed that fails requires investigation before claiming passage." Nothing enforces this. An agent (human or otherwise) can iterate seeds silently and only log the passing one. Nothing in the gate report ties the seed to something outside the operator's control.

**Why it matters.** Every stochastic gate (G0a, G0b, G0c, G2, G3) is vulnerable. The multi-session protocol relies on gates as the trust anchor ("trust gates, not prose" — README §4). Break the gates and the whole protocol degrades to "trust prose".

**Fix.** Derive the gate seed deterministically from `sha256(scenario_normalized_toml || git_commit_sha)[:8]` — call it the **gate seed**. For gate runs the CLI ignores `--seed` overrides and stamps the derived seed into `gate_report.json`. Add to `nukebench gate`: if `--seed` is passed with a gate flag, exit with code 2 (usage error). Re-running with a different git commit is fine (that's a code change, which is auditable via git); re-running with a different scenario is a different gate.

Belt-and-braces: add a `gate_attempts` counter to the artifact directory (`gate_report.json.d/attempt_<N>.json`) that CI archives. Anomalous attempt counts are visible in PR review.

### B-05 [MAJOR] Quasi-static eigen refresh is optimistic during disassembly — will produce systematic yield bias — `01-physics.md` §4 (E3), `05-module-transport.md` §3

**What is wrong.** The default `eigen_refresh_gens = 10` × `generation_time_s = 1e-8` = 100 ns between refreshes. Between refreshes the geometry is frozen. Late disassembly velocities reach several km/s ≈ 1e5–1e6 cm/s at Trinity scale, and even 1e7 cm/s (100 km/s) is reported for some kinetic-phase models. Verified numerics on a 3.5 cm compressed pit:

- at 1e6 cm/s per generation-refresh window: Δr = 0.1 cm → 2.9 % of r → ~6 % density → ~12 % Δk
- at 1e7 cm/s: Δr = 1.0 cm → 29 % of r → quasi-static breaks

The spec has an escape hatch "or immediately upon any hydro geometry update", but `hydro.dt_s = 1e-8` = one shake = one generation, which would collapse `eigen_refresh_gens = 10` to `= 1`. That is not what the example tally shows: 566 generations with 57 eigen calls = one refresh per 10 gens exactly, i.e., the hydro-update trigger did not fire. So either the hydro is not moving (bad) or the trigger is not wired (bad).

**Why it matters.** Yield is set by the disassembly quench. If k is stale during that quench, yield is biased — high if k is over-estimated near quench, low if under. G2 (yield ∈ [15, 25] kt) has enough bandwidth to absorb this bias unnoticed, but the sim will not correctly rank interventions (e.g., "does adding tamper thickness raise yield?") because the ranking depends on the quench dynamics that were mis-modelled.

**Fix.** Two changes:

1. Make the refresh cadence adaptive: refresh whenever the max radius change since the last eigen exceeds `eig_geom_tol` (new SIM constant, default 2 %); or after `eigen_refresh_gens` — whichever comes first. Add `eig_geom_tol` to `constants.toml` (SIM tag).
2. In `08-validation.md` add a non-gating cross-check: single burst re-run with `eig_geom_tol = 0.5 %` (quasi-continuous refresh); report yield delta. If Δyield / yield > 5 %, the coarse mode is biased — either amend the default or note it in the run.

Also update the tally example so `eigen_calls` is consistent with hydro-triggered refresh (see A-02).

### B-06 [MAJOR] E3a assumes a single ν̄ — the layered assembly has multiple fissioning isotopes with different ν̄ — `01-physics.md` §4, `05-module-transport.md` §3, `03-data-contracts.md` §2

**What is wrong.** E3a: `F_n = k · N_n / ν̄`. The spec quotes ν̄ = 2.9 (Pu-239). But the tally schema explicitly separates U-238 tamper fissions (C-021: ν̄_U-235 ≈ 2.4; U-238 fast ν̄ ≈ 2.8). The correct effective ν̄ is a fission-source-weighted average, not a constant. Using ν̄ = 2.9 for the *whole* assembly biases F_n and hence yield in the direction of the Pu contribution.

For Trinity where ~80 % of fissions are Pu-239 the error is a few percent (small vs G2 band) but the per-isotope split feeding `tally.burnup.pu_fraction` and `tally.burnup.tamper_yield_fraction` is derived from `F_n` × layer-fission-fractions (`05` §3). If the total F_n is biased, both readouts move together — mask a modelling error.

**Why it matters.** The spec's whole hard-boundary story (`00-overview.md` §3.5: "keep conflated quantities separate") is undermined if the numerator (F_n) uses one ν̄ and the split-by-isotope uses another. Also directly interacts with the accuracy expectations of G2's tamper_yield_fraction ∈ [0.10, 0.30] band.

**Fix.** Replace `ν̄` in E3a with `ν̄_eff(t)`, the fission-source-weighted average computed at each eigen refresh:

```
ν̄_eff = Σ_i (ν̄_i · S_i) / Σ_i S_i
```

where `S_i` is the isotope-resolved fission source produced by the last eigen. `physics/eigen` already runs per-isotope collisions (04 §3), so `S_i` is available. Add a unit test in M3-T1: fixed k = 2, Pu-only assembly ⇒ F_n matches closed form with ν̄ = ν̄_Pu; mixed assembly ⇒ ν̄_eff computed vs recomputed by hand.

Also amend `01-physics.md` §4 language: replace bare "ν̄" with "ν̄_eff" and add one line defining it.

### B-07 [MAJOR] `G0c` claims "population series identical under renormalization alignment" — bit-identical claim contradicts the stochastic nature of the k it consumes — `08-validation.md` §G0c, `05-module-transport.md` §6

**What is wrong.** G0c step 2: "population series identical under renormalization alignment". §6 justifies it as "exact, since E3 arithmetic is generation-discrete". But E3a is `N_{n+1} = k · N_n`, and k is a stochastic eigenvalue estimate that differs between backends (G0c step 2's *own first clause* says `|k_ref − k_gpu| ≤ 3σ` — i.e., they are numerically different). Feed different k into deterministic recurrence and you get different N. So "identical" is impossible unless both backends run the *same* eigen (they don't).

**Why it matters.** M4-T3 DoD is `G0c passes`. If the criterion as written is unsatisfiable, an implementer either invents a workaround (silently loosen the tolerance in code — spec violation) or freezes k to a shared oracle value (destroying the differential test).

**Fix.** Replace "identical under renormalization alignment" with a statistical criterion consistent with the first clause:

### B-09 [MAJOR] E1c fission-progeny formula mixes implicit-capture and analog language — implementer will pick wrong semantics — `01-physics.md` §2 (E1c), `05-module-transport.md` §1

**What is wrong.** §2 preamble: "Few-group... Monte Carlo with implicit capture (weight-based)". E1c: "**Fission: kill incoming neutron**, bank `⌊w·ν̄·(Σ_f/Σ_t)·(1/k_gen) + ξ⌋` progeny into the fission bank...". Under implicit capture, the incoming neutron is **not** killed — its weight is reduced and it continues (typically as a scattered neutron, since scattering share is `Σ_s/(Σ_s+Σ_c)`). "Kill incoming neutron" is analog absorption language. The formula `w·ν̄·(Σ_f/Σ_t)` — banking fission progeny proportional to the fission-branch fraction — is implicit-capture language. Both cannot be right.

**Why it matters.** ref/ and gpu/ implementers can pick different conventions from the same spec and G0c will show a small but systematic k bias that no one can trace to a spec sentence.

**Fix.** Commit to one convention and delete language for the other. Recommended (matches the WARP/Shift precedent cited): analog reaction sampling, implicit capture on absorption. Rewrite E1c as:

> E1c (collision): sample isotope ∝ n_i · Σ_t,i . Sample reaction ∈ {scatter, absorb} with probabilities Σ_s,i / Σ_t,i and Σ_a,i / Σ_t,i. On absorb: bank fission progeny with expected count `w · (Σ_f,i / Σ_a,i) · ν̄_i / k` (implicit capture on absorption); the incoming neutron dies. On scatter: sample downscatter group from transfer matrix, resample isotropic direction, weight unchanged.

The `w · (Σ_f,i/Σ_a,i) · ν̄_i / k` form makes fission implicit-*within absorption*, keeping the analog scatter loop clean. Update §5 (RefTransport algorithm) to match.

### B-12 [MAJOR] RNG counter management for fission progeny is unspecified — will show up as G0c divergence — `04-module-core.md` §2, `05-module-transport.md` §1 and §6, `appendix/constants.md` C-907

**What is wrong.** Stream registry gives distinct stream IDs per purpose (source, flight, collision, fission, scatter, hydro, render). But when a neutron fissions and produces ν̄ progeny, each child needs its own (stream_id, counter). Two natural options:

(a) child inherits parent's Philox stream at the parent's current counter; each child forks a sub-stream by index.
(b) child gets a globally unique particle ID from a per-generation atomic counter and uses that ID as its `stream` field.

Option (a) requires a hierarchical counter scheme that ref/gpu must implement identically. Option (b) requires the global counter to increment in the same order on both backends — trivially false on GPU because thread scheduling is nondeterministic.

**Why it matters.** G0c ("same seed ⇒ identical tallies on any backend, any thread count", `01-physics.md` §9) becomes unattainable if ref uses one convention and gpu uses another. It will manifest as a small but persistent k bias in the differential harness.

**Fix.** Commit to option (a) with an explicit scheme, e.g.:

- Each history has a `(stream, counter)` pair.
- On fission producing N progeny, child i (i = 0..N-1) gets stream = `mix(parent.stream, parent.counter, i)` where `mix` is a documented 64-bit function (e.g., splitmix64 of the three inputs). Child counter starts at 0.
- Document `mix` in `04-module-core.md` §2. Add a KAT: given (stream=42, counter=1000, i=3), `mix(...)` returns a specific 64-bit value; both ref/ and gpu/ must reproduce.

Ensures G0c is reachable.

### B-15 [MAJOR] Multi-session claim mechanism has no conflict resolution — parallel claims race on PROGRESS.md — `spec/README.md` §5 (claim), §7 (parallel)

**What is wrong.** The claim is "edit PROGRESS.md, commit". README §7 says PROGRESS.md conflicts: "keep both task rows, human resolves". But:

- Two sessions both fetch main, both edit the same task row to `in_progress`, both commit locally. Both push. Second push loses to `git push --force` or races on non-fast-forward. If merge, then the row is present twice with two `claimed_by` values — silent duplication.
- If a session crashes with an unpushed claim, no one knows.
- 24 h stale-claim heuristic is textual — no automated re-claim, no CI enforcement.
- "Human resolves the NEXT ACTION line" — but this is meant to be an agent-driven project.

**Why it matters.** Under actual parallelism (which ADR-009's M4 retiming actively encourages: "M4-T1/T2 in parallel with M2/M3"), duplicate work is almost guaranteed within the first two weeks.

**Fix.** Replace "edit PROGRESS.md, commit" with a more forgiving primitive:

1. **Lock file per task.** `spec/.locks/Mx-Ty.lock` is created via `git add`+commit with `{session_id, timestamp, git_sha}`; the commit message is `claim Mx-Ty`. Committing a lock file that already exists (git merge conflict) is the coordination point — the earlier-timestamped commit wins by convention. A session that loses the race deletes its lock and picks another task.
2. **PROGRESS.md is derived, not authoritative.** A CI job regenerates the Tasks table from lock files and open PRs. Race-losing sessions can't accidentally overwrite it.
3. **Stale claim = lock older than N wall hours AND commit not present on origin.** Add a tool `tools/reap_stale_locks` that CI runs daily.
4. **VERIFY as claim precondition.** A session may not create a lock file if the `VERIFY:` command in PROGRESS.md fails against its worktree.

If (1)–(4) are heavier than the project wants, minimum change: mandate one branch per task (`task/Mx-Ty-*`) and forbid direct main commits during in-flight work; use GitHub branch-existence as the de-facto lock. Document explicitly in README §5.

### C-14 [MINOR] `nukebench diff` compares two run directories but scenario/seed identity is not enforced — `06-frontends.md` §1, `08-validation.md` §G0c

**What is wrong.** Signature `nukebench diff --run-a --run-b` implies "any two runs". But G0c requires "same scenario + seed on ref and gpu backends". If someone passes two runs with different seeds `nukebench diff` will happily report a p-value that is meaningless.

**Fix.** `nukebench diff` MUST compare `run.json.scenario_sha256` and `run.json.seed` and exit code 2 if either differs. Then G0c is well-defined.

### C-15 [MINOR] `docker` base `nvidia/cuda:13.1-devel-ubuntu22.04` may not exist by literal tag — `12-deployment.md` §3

### C-16 [MINOR] Log-scale renormalisation past 1e30 — the accumulator (F_cum, E_cum) may itself overflow — `01-physics.md` §4, `05-module-transport.md` §3

**What is wrong.** N is renormalised to 1.0 with exponent offset when N > 1e30. But F_cum and E_cum are also `k · N_n / ν̄` × generations, and if N is renormalised the accumulator must ALSO scale to the same exponent, or accumulate in log-space, or use compensated summation. The spec says "tallies use scaled weights" — but does not specify HOW.

**Fix.** Explicit algorithm: F_cum and E_cum stored as `(mantissa, exp_offset)` pair; on N renormalisation, F_cum is unaffected (it is a cumulative integer count of fissions, not a live population), but any live tally that scales with current weight (e.g., `population_series` log₁₀ N) must account for exp_offset. Add a unit test in M3-T1 that renormalises 3 times mid-burst and asserts F_cum unchanged compared to a no-renorm control at half-scale.

If it is a *layer of noise added for aesthetics*, that becomes a scope-boundary question (invented visual data).

**Fix.** Clarify: "Mottling comes from the fission_rate channel variance in the field dump; no additional noise is layered." If aesthetic noise IS wanted, add an explicit `noise_amplitude` SIM constant with rationale.

## E. Preserve — do not amend these

These are load-bearing decisions worth defending during triage. Any rework should keep them intact.

1. **Separation of `nscore` from frontends (D7).** Correct architecture for a project that has to serve CLI/farm/studio/cinema off one code base. Do not let a studio task slide physics into `app/`.
2. **Two-tier ref/gpu with G0c differential validation (D1).** This is the debug backbone — without it, the GPU work is unreviewable. The one caveat is the "identical" wording (B-07).
3. **Yield as a range, band-based gates (00 §3.6, G2).** Correct pattern for classified point-values. Preserve.
4. **Constants file as single source of truth (01 §8, appendix).** Structurally right, even where the appendix needs cleanup (A-06).
5. **Checkpoint/resume as a first-class gate (D9, T-resume).** Cloud reality (spot instances) makes this essential; the design has thought about Philox counter safety correctly.
6. **Amendment protocol + append-only DECISIONS.md.** The right way to run a multi-session project; do not soften.
7. **PROGRESS.md `VERIFY:` line as a live probe (README §4).** Concept is right — just fix the initial no-op (B-16).
8. **Separation of Pu burn-up vs U-238 tamper yield (00 §3.5, tally schema).** The single most important boundary constraint in the physics; loud UI enforcement is on the money.
9. **Sweep objective enforced by schema (D8, ADR-007).** Concept is right — just make the enforcement mechanical, not label-based (B-13).
10. **Task IDs stable and referenced from commits + PROGRESS + SESSIONS.** Great for audit; do not renumber.
11. **`08-validation.md` §3 rules** ("no seed-shopping, no gate-by-inspection") are the right policy — just needs enforcement teeth (B-04).
12. **ADR-009 process pattern.** The way the toolchain amendment was done (evidence → ADR → CHANGELOG → spec updates) is exactly the mode the project needs to run in. Preserve as the template for future amendments.
13. **Log-scale population series (01 §4, tally schema).** Correct choice for a system that renormalises past 1e30; do not weaken.
14. **Two-buffer AnalyticSphereTracker as the permanent oracle (D2).** Right decision — closed-form ray-sphere is exact and faster than any BVH for concentric spheres. OptiX as a Stage-3-only addition is the right sequencing.
15. **The "public/declassified only" scope frame (00 §3).** Every subsequent design choice is coherent with it; the boundary language is precise. Preserve verbatim.

## F. Verdict + top 5 fixes

### Overall verdict: **AMEND-THEN-SHIP**

The spec's architecture, scope discipline, and multi-session protocol are the strongest parts and should not be reworked. The physics substrate has several precise but wrong-labelled quantities (A-04, C-01), and the data contracts have numeric-consistency defects in their canonical examples that will fail the very tests M0/M1 write against them (A-01, A-02, A-03). None of the defects reach "throw out and restart" — they are targeted amendments to specific sections, and the amendment protocol is well-designed to absorb them. A single triage session using ADR-010 through ADR-020 (or one omnibus ADR covering all blockers) can close the top 8 items in a day. After that, M0-T1 is safe to begin.

### Top 5 fixes that MUST happen before M0-T1 starts

Ordered by dependency, not by severity — each one unblocks the next:

1. **A-06 (appendix cannot be parsed by gen_constants).** M0-T3 cannot run without this. Add the strict-typed sibling file. Everything else compiles constants at some point.
2. **A-01 (canonical scenario TOML is invalid).** M0-T5 loader tests fail here. Rewrite the `[[layers]]` block. Also unblocks C-04 (override syntax) which can be resolved in the same amendment.
3. **A-04 (Guderley exponent γ mislabel).** Cheap to fix (three files), and it's a physics fact — no reason to carry it forward one more milestone.
4. **A-05 (gates.toml owner ambiguity).** M1-T5 will hit this on day one. Move to M1-T4 explicitly.
5. **A-08 (bootstrap prompt omits DECISIONS.md).** Every future session inherits the wrong reading habit if this is not fixed at the top of the tree. One-line change.

Two runners-up that are also cheap and remove real ambiguity: **A-02** (tally.json order-of-magnitude), **A-07** (OptiX env var naming).

### Preserve list — punt into ADR triage but do not re-open

Items in **Section E** are the load-bearing pieces. When the amendment session goes through Sections A/B/C, it should explicitly note "preserving [E-1..E-15]" so future re-triage does not accidentally re-litigate them.
