## 1. What this project REALLY is (the gist + the soul + the distinction)

**On the surface:** a spec-first, multi-session, GPU Monte-Carlo simulator of the 1945 Trinity
"Gadget" / Fat Man device — neutron transport → k-eigenvalue criticality → α-mode burst kinetics
→ implosion/disassembly hydro → (eventually) volumetric fireball + chain-reaction rendering.
Built **exclusively from public/declassified literature**. Public GitHub, MIT
(<https://github.com/bochen2029-pixel/nuclear-sim>).

**But that's the skin. The soul — the WHOLE POINT — is the total package:** an **interactive 3D
visualizer of the demon-core fission chain reaction**, done right. Zoom into the plutonium pit,
**slow time down** (a slider from ~5 s to ~5 min), and *watch* a bundled, representative cloud of
~10,000–50,000 3D "atoms" split in a rapid cascade in a true volumetric sphere. **It must be
real** — every rendered atom a genuine sampled fission from the underlying Monte-Carlo, the
graphics *tracking* the math, never decoration on top of it. In the owner's words: *"without this
being visualized and matching the core underlying math, the rest of it is meaningless and just a
sideshow — this is the main course."*

**The distinctions that define this project — hold all of them:**

1. **Nothing faked; everything emergent, not hardcoded.** Detonate-vs-fizzle is not a scripted
   branch — it EMERGES from whether the core goes prompt-supercritical and self-quenches
   (`generate_run`). The chain-reaction atoms the viz shows are real `FissionSource::sites`.
2. **"All real, or simulated-but-honest."** The honesty ladder: `simstub.js` (fake) → **real
   transport + SIM-but-loadable cross sections (WHERE WE ARE)** → real transport + *cited* xs
   (with `fast4`). The ALGORITHM is real now; `fast4` makes the NUMBERS cited/benchmark-proven.
   Every SIM value is tagged SIM and said so. **Fabricated cited data is the single failure the
   whole provenance discipline exists to prevent** (see §7.4 / BLK-14).
3. **Time is slowed way down, but it is ONE continuous event.** implosion → criticality → α
   burst → disassembly → fireball is a single staged clock (D6: BURST/HYDRO/FIREBALL phases,
   t=0 = outermost-HE initiation). The viz slows it so you can watch, but it never fakes a cut
   between phases — the SimClock maps render/wall time to sim time continuously.
4. **Scale via the CORRECT physics.** Inspired (negatively) by a naive 2D JS criticality viz that
   capped at ~2000 atoms because it modelled atoms as O(N²)/step all-pairs particles. The thesis:
   do it 100× better, in 3D, for the whole device — by tracking **neutrons** (O(N), independent,
   ≥1e6/gen on GPU), not atoms. The "atoms splitting" are fission EVENTS. **Never architect the
   chain-reaction viz as O(N²) all-pairs.**
5. **The product & the differentiator.** Eventual **Steam release** — a visual, interactive 3D
   sandbox (spirit of the owner's *DF-41 Simulator*). **Public MIT GitHub = the ENGINE/spec;**
   Steam = the polished visual `nukestudio` layer (M7). Headless frontends (nukebench, nukefarm
   MCTS sweeps) are engine + validation, NOT the shelf product. The differentiator vs a novelty
   sim: **every visual is driven by real, benchmark-provable physics** — which is why the gates
   (and `fast4`) matter for the PRODUCT, not just academic rigor.

**Scope guardrails (hard, `00 §2–§3`):** public/declassified only; every constant carries a
citation + status. Classified gaps (exact peak k, Bethe–Feynman coefficients, lens contours) are
NOT filled — published *bands* only, never invented point values. Interactive single-point
exploration is in scope (`non_canonical`, never gate evidence); automated search over *physical*
axes toward an objective is OUT (enforced mechanically by `axis_class` + `ScoreKind` — which
M5-T3-a/M5-T4 implement).

## 7. WHAT TO WATCH OUT FOR (traps + hard-won insights — read every one)

### 7.1 The density-coupling insight (the single most important physics one)
`Σ ∝ ρ`. For ANY moving geometry use **`ref_eigen_fn_masscons`** (scales ρ mass-conservingly,
`ρ/ρ₀ = (r₀/r)³`), never `ref_eigen_fn` (fixed density; static assemblies only) — else
compression/expansion read BACKWARDS. It's uniform (bare core exact); the full multi-layer device
needs per-layer scaling + `fast4`.

### 7.2 The fusion architecture boundary (C++ = DATA; JS = presentation)
`generate_run` returns **DATA ONLY** (tally/run/samples + emergent detonate/reasons/yield). The JS
adapter (`studio-adapter.js`, replacing `simstub.js`) reconstructs the presentation closures
(`flux(t)`/`compression(t)`) from that real data; `main.js` is unchanged EXCEPT that
evaluate/generateRun become **async** (a real eigen is seconds — debounce + show "running"). All
three binding mechanisms (dev-server chosen; WASM/native later) wrap the SAME
`evaluate_json`/`generate_run_json` surface. (In `docs/FUSION-BINDING.md` + `viz-adapter-worklog.md`.)

### 7.3 The shared working tree with the -e (viz) session
The parallel viz session develops in the SAME tree (`C:\NUCLEAR`); its uncommitted `viz/` edits +
`.zcode/` appear in your `git status`. **Rules:** stage EXPLICIT paths (`git add <path> …`), NEVER
`git add -A`; verify `git diff --cached --name-only` has no unintended `viz/`/`.zcode` before EVERY
commit. When the owner directs viz work (as this session), build it as NEW files only and stage
those files explicitly — never sweep in the -e session's uncommitted `main.js`/`simstub.js`/etc.

### 7.4 The `fast4` discipline (never cross this line)
`fast4` = the cited 4-group xs dataset (~450 physical values, M1-T4a-2), **owner-provided**,
**MUST NOT be invented** — fabricated cross sections are the single failure the whole provenance
discipline exists to prevent. BLK-14 forbids an autonomous session seeking ICSBEP access. Same
discipline for the M5-T5 container base-image digest (don't invent it — verify via `docker pull`,
which needs docker/registry). Use synthetic-but-loadable xs (tagged SIM) where needed and say so;
surface the ask, don't stall the whole session on it.

### 7.5 CI / git cadence (bit us; watch for it)
Space out `main` pushes — rapid pushes trigger a GitHub Actions **concurrency cancel-cascade**.
Watch each push to green (`gh run watch <id> --exit-status`) before layering the next task. **gcc
(Linux CI) finds what MSVC does not** — expect it on new modules; MSVC-clean ≠ CI-clean. Merge only
green (`--no-ff`, message via a temp file). **The machine can sleep overnight** and kill a `gh run
watch` (exit 4) while the CI run itself keeps running on GitHub's servers and finishes fine —
re-check the specific run's `conclusion` by `headSha`, don't trust a failed *watch* as a failed CI.

### 7.6 ASCII-only Catch2 test names
A `—` (em-dash) or a `,` (comma) in a `TEST_CASE` name breaks ctest↔Catch2 matching ("No test
cases matched"). Keep titles ASCII, no commas. And the case text must NOT repeat the module prefix
(TEST_PREFIX adds it — else you get `store.store.…`).

### 7.7 Browser dev-server: CORS preflight
A cross-origin `POST` with a JSON content-type triggers an `OPTIONS` **preflight**; a server that
only implements GET/POST returns 501 → the browser blocks the POST ("Failed to fetch"). `curl`
skips preflight, so a host smoke passes while the browser fails. `studio_server.py` now has
`do_OPTIONS`; keep it if you touch the server.

### 7.8 Protocol traps (recurring, from ONBOARDING §4)
Read the module spec (`04`/`05`), not just the data contract (`03`). "Within 1σ" acceptance is a
coin flip (use 3σ + a mean-pull check). Never tune a test to pass. A vacuous check proves nothing.
Measure, don't estimate. Probe names anchored (`^<module>\.`). Constants from `ns::consts`; gate
thresholds from `gates.toml`. Keep the anchored-probe sum true when you add tests.
